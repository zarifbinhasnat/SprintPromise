## 🐍 PYTHON — Memoization

### Intuition

Yesterday's `fib()` recomputes the same smaller answers over and over because it has no memory between calls. Memoization is that memory: store the result of `fib(k)` the first time it's computed, and return the stored value instead of recomputing it every time after. Same recursive structure, same base case — the only change is a lookup before doing any work.

### The Essentials — manual memo dict

```python
def fib_memo(n, cache=None):
    if cache is None:
        cache = {}
    if n in cache:          # already solved this one — just return it
        return cache[n]
    if n <= 1:
        return n
    cache[n] = fib_memo(n - 1, cache) + fib_memo(n - 2, cache)
    return cache[n]
```

The recursive calls are identical to yesterday's naive version — the only addition is the `if n in cache: return cache[n]` check at the top, and storing the result before returning it.

### The Essentials — `functools.lru_cache`

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib_lru(n):
    if n <= 1:
        return n
    return fib_lru(n - 1) + fib_lru(n - 2)
```

`lru_cache` does exactly what the manual dict did — keeps a cache keyed on the function's arguments — but as a decorator, with no cache variable to thread through every call. `maxsize=None` means the cache never evicts old entries; a real `maxsize=N` would.

### Proving the speedup

```python
import time

start = time.perf_counter()
fib_naive(28)             # naive recursive, no memo
naive_time = time.perf_counter() - start

start = time.perf_counter()
fib_lru(28)                # memoized
memo_time = time.perf_counter() - start

print(f"naive: {naive_time:.4f}s, memoized: {memo_time:.6f}s")
# naive: 0.0418s, memoized: 0.000004s — roughly a 10,000x difference at n=28,
# and the gap widens fast as n grows, because naive is O(2^n) and memoized is O(n)
```

### The gotcha

`lru_cache` keys its cache on the function's exact arguments, which means those arguments have to be **hashable** — ints, strings, and tuples work; a `list` argument raises `TypeError: unhashable type`. It's built for pure functions of simple inputs, not for caching results that depend on mutable state.

## 🧩 DSA — Fibonacci Number *(Easy · Recursion)*

**NeetCode / LeetCode:** https://leetcode.com/problems/fibonacci-number/

### The Problem

`F(0) = 0`, `F(1) = 1`, and `F(n) = F(n-1) + F(n-2)` for `n > 1`. Given `n`, return `F(n)`.

### Reading the problem like an engineer

This is the recurrence itself, not a word problem hiding one — which makes it the cleanest place to see memoization's effect with nothing else in the way. The call tree is identical in shape to yesterday's Climbing Stairs: two recursive calls per level, doubling at every level, the same subproblems recomputed from multiple branches.

### Approach 1 — Brute Force (write this first, always)

```python
def fib_brute(n):
    if n <= 1:
        return n
    return fib_brute(n - 1) + fib_brute(n - 2)
    # Time:  O(2^n) — call tree doubles at every level
    # Space: O(n) — recursion depth
```

### Approach 2 — Memoized Recursion (the insight)

```python
def fib_memo(n, cache=None):
    if cache is None:
        cache = {}
    if n in cache:
        return cache[n]
    if n <= 1:
        return n
    cache[n] = fib_memo(n - 1, cache) + fib_memo(n - 2, cache)
    return cache[n]
    # Time:  O(n) — each fib_memo(k) does its own work exactly once
    # Space: O(n) — cache dict + recursion depth
```

### Walkthrough on `n = 4`, showing what the cache saves

```
fib_memo(4)
  needs fib_memo(3) + fib_memo(2)
    fib_memo(3) needs fib_memo(2) + fib_memo(1)
      fib_memo(2) needs fib_memo(1) + fib_memo(0) -> computes 1, CACHES cache[2]=1
      fib_memo(1) -> base case, returns 1
    fib_memo(3) = 1 + 1 = 2, CACHES cache[3]=2
  fib_memo(2) -> cache[2] EXISTS -> returns 1 INSTANTLY, no recursion at all
fib_memo(4) = 2 + 1 = 3
```

Without the cache, that second `fib_memo(2)` call would re-run the exact same two recursive calls `fib_memo(3)` already paid for. With it, it's a dict lookup.

### Why memoization, specifically, and not bottom-up here

Both fix the same waste. Memoized recursion keeps the original top-down recursive shape — you write the recurrence exactly as stated and let the cache handle efficiency — while yesterday's bottom-up DP restructures the same logic into an explicit loop from the base cases up. Memoization is usually the faster thing to *write* correctly (the recursion mirrors the problem statement directly); bottom-up is usually more memory-efficient (Day 12's version used O(1) space; this cache uses O(n)).

## ⚡ FASTAPI — CORS Middleware

### Intuition

CORS (Cross-Origin Resource Sharing) is a browser rule, not a server rule: by default, JavaScript running on `http://localhost:3000` is blocked from reading a response from `http://localhost:8000`, even if the server processed the request perfectly and sent a valid response — the browser throws it away before your frontend code ever sees it. `CORSMiddleware` tells the browser, via response headers, which origins are allowed to actually read the response.

### The Essentials

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],   # exact origins only
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

This has to be registered via `add_middleware`, not the `@app.middleware("http")` decorator from Day 8 — `CORSMiddleware` is a class FastAPI ships, not a function you write, and it needs to run *before* your routes so it can attach the right headers to every response, including ones your own middleware never touches.

### What actually happens on the wire

```
1. Browser sends a request from http://localhost:3000 to this API.
2. For "simple" requests, the browser just checks the response's
   Access-Control-Allow-Origin header before handing the body to your JS.
3. For anything more complex (custom headers, non-GET/POST methods), the
   browser sends a "preflight" OPTIONS request FIRST, asking permission —
   CORSMiddleware answers that automatically; you never write an OPTIONS route.
4. If the requesting origin isn't in allow_origins, the browser silently
   drops the response — no Access-Control-Allow-Origin header comes back,
   even though the server actually ran the handler and returned 200.
```

That last line is the classic confusing bug: the server logs show a successful 200, but the frontend's `fetch()` call fails with a generic network error — because the failure happens in the browser, after the response already arrived.

## 🔗 COMBINED TASK — Wiring All Three

`GET /fib/{n}` uses today's `@lru_cache`-decorated Fibonacci function directly — the same recursion as the DSA solution above, just decorated instead of hand-rolled with a cache dict — and `CORSMiddleware` is configured so only `http://localhost:3000` can read any of this API's responses from a browser, verified by checking for the `Access-Control-Allow-Origin` header on both an allowed and a disallowed origin. Day 12's lifespan-managed request counter and Day 11's `StockNotFoundError` handler both continue running unchanged underneath.

```python
# main.py — Day 13 combined pieces

from functools import lru_cache
from fastapi.middleware.cors import CORSMiddleware

@lru_cache(maxsize=None)
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)


app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)


@app.get("/fib/{n}")
def fibonacci(n: int):
    return {"n": n, "value": fib(n)}
```

# fastapi/13_cors_middleware/main.py
# Run: uvicorn main:app --reload

from contextlib import asynccontextmanager
from functools import lru_cache
from fastapi import FastAPI, Depends, Request, status
from fastapi.middleware.cors import CORSMiddleware
from fastapi.responses import JSONResponse
from pydantic import BaseModel
from typing import List

app_state = {}


@lru_cache(maxsize=None)
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)


@asynccontextmanager
async def lifespan(app: FastAPI):
    app_state["request_count"] = 0
    yield
    app_state.clear()


app = FastAPI(title="Sprint Day 13", lifespan=lifespan)

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)


class StockNotFoundError(Exception):
    def __init__(self, stock_id: int):
        self.stock_id = stock_id


class StockIn(BaseModel):
    ticker: str
    prices: List[int]


stock_db = {}
next_id = 1


def get_stock_or_404(stock_id: int):
    if stock_id not in stock_db:
        raise StockNotFoundError(stock_id)
    return stock_db[stock_id]


@app.exception_handler(StockNotFoundError)
def stock_not_found_handler(request: Request, exc: StockNotFoundError):
    return JSONResponse(
        status_code=status.HTTP_404_NOT_FOUND,
        content={"error": "stock_not_found", "detail": f"stock {exc.stock_id} not found"},
    )


@app.middleware("http")
async def count_requests(request: Request, call_next):
    app_state["request_count"] += 1
    return await call_next(request)


@app.get("/")
def root():
    return {"message": "Sprint Day 13 is running.", "day": 13, "requests_so_far": app_state["request_count"]}


@app.get("/fib/{n}")
def fibonacci(n: int):
    return {"n": n, "value": fib(n)}


@app.post("/stocks", status_code=status.HTTP_201_CREATED)
def create_stock(payload: StockIn):
    global next_id
    stock_id = next_id
    stock_db[stock_id] = payload.model_dump()
    next_id += 1
    return {"id": stock_id, **stock_db[stock_id]}


@app.get("/stocks/{stock_id}")
def get_stock(stock_id: int, stock: dict = Depends(get_stock_or_404)):
    return stock

## 🔑 CONCEPT ANSWER

**Question:** "Memoization and yesterday's bottom-up DP both turn Fibonacci from O(2^n) into O(n) — so what's actually different between them?"

**Answer:** Both eliminate the same redundant work, but from opposite directions. Memoized recursion is **top-down**: you call `fib_memo(n)`, it recurses down toward the base cases exactly as the recurrence is stated, and a cache intercepts any call whose answer was already computed — the recursive structure of the problem is preserved untouched, and the cache is what makes it efficient. Bottom-up DP is the opposite: there's no recursion at all — you start at the base cases and iterate upward, computing each value once in order, keeping only what's still needed. The complexity is the same (O(n) time), but the memory profile usually isn't: memoized recursion needs a cache holding every computed value (O(n) space) plus recursion-depth stack frames, while yesterday's bottom-up `climb_stairs` only ever kept two numbers in flight (O(1) space) because it never needed to look further back than one step. Top-down is often easier to get right first — it mirrors the problem statement directly — bottom-up is usually the more memory-efficient version once you see the pattern.
