## 🐍 PYTHON — Comprehensions Deep-Dive

### Intuition

A comprehension is a loop that builds a collection, written as one expression instead of a `for` block with `.append()`. You already know the one-line filter shape from Day 4 (`{n: n*n for n in nums if n % 2 == 0}`). Today: nesting them, the lazy generator-expression variant, and knowing when a comprehension has gotten too dense to read.

### The Essentials

```python
# Nested comprehension — flatten a list of lists
matrix = [[1, 2, 3], [4, 5, 6], [7, 8, 9]]
flat = [n for row in matrix for n in row]
# [1, 2, 3, 4, 5, 6, 7, 8, 9]
# reads left-to-right like nested for loops would:
#   for row in matrix:
#       for n in row:
#           n

# Nested comprehension building a matrix, not flattening one
grid = [[r * c for c in range(3)] for r in range(3)]
# [[0, 0, 0], [0, 1, 2], [0, 2, 4]]

# Generator expression — same syntax as a list comprehension, but ()
# instead of [] — values are produced lazily, one at a time, not all at once
squares_gen = (n * n for n in range(1_000_000))
next(squares_gen)   # 0 — nothing else has been computed yet
sum(n * n for n in range(10))   # generators work directly with sum(), max(), etc.

# Comprehension vs. map/filter — same result, different style
nums = [1, 2, 3, 4, 5]
evens_comp = [n for n in nums if n % 2 == 0]
evens_mapfilter = list(filter(lambda n: n % 2 == 0, nums))
# Prefer the comprehension — it reads left to right and doesn't need a lambda
```

### When NOT to use a comprehension

```python
# Too dense — this technically works but nobody should have to parse it:
result = [x * y for x in range(10) if x % 2 == 0 for y in range(10) if y % 3 == 0 if x != y]

# If you need more than one nesting level or more than one condition,
# a plain loop is the more readable, more debuggable choice:
result = []
for x in range(10):
    if x % 2 != 0:
        continue
    for y in range(10):
        if y % 3 != 0 or x == y:
            continue
        result.append(x * y)
```

A comprehension is a readability tool, not a rule to follow at all costs — the moment you can't read it back in one glance, it's no longer doing its job.

## 🧩 DSA — Move Zeroes *(Easy · Two Pointers)*

**LeetCode:** https://leetcode.com/problems/move-zeroes/

### The Problem

Given an array `nums`, move all `0`s to the end while maintaining the relative order of the non-zero elements — in place, without making a copy.

### Reading the problem like an engineer

Strip the wrapper: *"Walk through and compact all the non-zero values to the front, in order — then whatever's left over must be zeroes."* This is Day 7's in-place two-pointer swap again, but the two pointers move at different speeds this time: one (`i`) scans every element, the other (`insert_pos`) only moves when there's actually something non-zero to place.

### Approach 1 — Brute Force (write this first, always)

```python
def move_zeroes_brute(nums):
    non_zeroes = [n for n in nums if n != 0]   # today's comprehension, applied
    zero_count = len(nums) - len(non_zeroes)
    nums[:] = non_zeroes + [0] * zero_count
    # Time:  O(n)
    # Space: O(n) — non_zeroes is a full second list
```

### Approach 2 — Two Pointers, Different Speeds (the insight)

```python
def move_zeroes(nums):
    insert_pos = 0
    for i in range(len(nums)):
        if nums[i] != 0:
            nums[insert_pos], nums[i] = nums[i], nums[insert_pos]
            insert_pos += 1
    # Time:  O(n) — one pass
    # Space: O(1) — swaps happen in place, no extra list
```

### Walkthrough on `nums = [0, 1, 0, 3, 12]`

```
insert_pos=0
i=0, nums[0]=0 -> skip
i=1, nums[1]=1 -> swap nums[0],nums[1] -> [1,0,0,3,12]  insert_pos=1
i=2, nums[2]=0 -> skip
i=3, nums[3]=3 -> swap nums[1],nums[3] -> [1,3,0,0,12]  insert_pos=2
i=4, nums[4]=12 -> swap nums[2],nums[4] -> [1,3,12,0,0]  insert_pos=3
-> [1, 3, 12, 0, 0]
```

### Why `insert_pos` is the whole trick

`i` scans every index unconditionally; `insert_pos` only advances when a non-zero value actually gets placed — so `insert_pos` always points at the next open slot for a non-zero value, and everything between `insert_pos` and `i` is guaranteed to be zeroes waiting to get swapped forward. Two pointers moving at different speeds, one tracking "where am I looking" and the other tracking "where does the next real value go," is a pattern that reappears constantly in in-place array problems.

## ⚡ FASTAPI — Dependency Injection

### Intuition

Every route so far has repeated the same "look up the stock, 404 if missing" check. `Depends()` lets you pull that logic out once and have FastAPI run it automatically before the route body — the same "don't repeat yourself" instinct that made you build `is_palindrome()` as a standalone function instead of copy-pasting it into every endpoint.

### The Essentials

```python
from fastapi import FastAPI, Depends, HTTPException, status

app = FastAPI()
stock_db = {}

def get_stock_or_404(stock_id: int):
    if stock_id not in stock_db:
        raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail=f"stock {stock_id} not found")
    return stock_db[stock_id]

@app.get("/stocks/{stock_id}")
def get_stock(stock_id: int, stock: dict = Depends(get_stock_or_404)):
    return stock
    # get_stock_or_404 already ran, already 404'd if needed —
    # by the time this line executes, `stock` is guaranteed to exist

@app.delete("/stocks/{stock_id}")
def delete_stock(stock_id: int, stock: dict = Depends(get_stock_or_404)):
    del stock_db[stock_id]
    return {"deleted_id": stock_id, "ticker": stock["ticker"]}
    # same lookup-or-404 logic, zero duplication
```

### Why this is worth learning now, not later

`Depends()` looks like a small trick today (one repeated `if stock_id not in stock_db` check), but it's the exact mechanism you'll use for authentication (`Depends(get_current_user)`), database sessions (`Depends(get_db)`), and pagination params, later in this track. Learning it on a lookup-or-404 check — something you already understand completely — means the concept is already familiar by the time the stakes are higher.

## 🔗 COMBINED TASK — Wiring All Three

`move_zeroes` becomes an endpoint that compacts a stock's price history (pushing every `0` — a day with no trading — to the end), and it's built on the `get_stock_or_404` dependency instead of a manually repeated check, reinforcing today's FastAPI pattern on a real route.

```python
# main.py — Day 9 combined endpoint

def move_zeroes(nums):
    insert_pos = 0
    for i in range(len(nums)):
        if nums[i] != 0:
            nums[insert_pos], nums[i] = nums[i], nums[insert_pos]
            insert_pos += 1
    return nums


@app.get("/stocks/{stock_id}/compact-prices")
def compact_prices(stock_id: int, stock: dict = Depends(get_stock_or_404)):
    prices = list(stock["prices"])
    move_zeroes(prices)
    return {"id": stock_id, "ticker": stock["ticker"], "compacted_prices": prices}
```

## 🔑 CONCEPT ANSWER

**Question:** "What's the practical difference between a list comprehension `[n*n for n in nums]` and a generator expression `(n*n for n in nums)`, and when would the memory difference actually matter?"

**Answer:** A list comprehension computes every value immediately and holds the entire result in memory as a list; a generator expression computes nothing up front — it produces one value at a time, on demand, as something iterates over it (a `for` loop, `sum()`, `next()`). For a small list this difference is invisible, but it matters the moment the sequence is large or unbounded: `sum(n * n for n in range(100_000_000))` never holds more than one squared value in memory at a time, while the list-comprehension version would try to build and hold a 100-million-element list first. The rule of thumb: use a generator expression when you're going to consume the values once, in order (feeding them into `sum()`, `max()`, another loop), and reach for a list comprehension only when you actually need to index into the result, iterate it more than once, or need `len()` on it.
