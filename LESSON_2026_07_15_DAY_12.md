## 🐍 PYTHON — Recursion

### Intuition

A recursive function is one that calls itself, on a smaller input, until it hits a case simple enough to answer directly without calling itself again. That's it — two parts, always: a **base case** (the stopping condition, answered directly) and a **recursive case** (do a little work, then call yourself again on something smaller). Miss the base case, or fail to actually shrink the input, and you get infinite recursion — Python will eventually raise `RecursionError`.

### The Essentials

```python
def countdown(n):
    if n <= 0:            # base case — stop here
        print("liftoff")
        return
    print(n)
    countdown(n - 1)      # recursive case — same function, smaller input

countdown(3)   # 3, 2, 1, liftoff
```

```python
def sum_to_n_recursive(n):
    if n == 0:
        return 0
    return n + sum_to_n_recursive(n - 1)

sum_to_n_recursive(5)   # 15 — same answer as a for-loop, different mechanism
```

### Tracing the call stack by hand

```
sum_to_n_recursive(3)
  -> calls sum_to_n_recursive(2)
       -> calls sum_to_n_recursive(1)
            -> calls sum_to_n_recursive(0) -> returns 0   (base case hit)
       <- 1 + 0 = 1
  <- 2 + 1 = 3
<- 3 + 3 = 6
```

Nothing gets *added* until the base case returns and the calls start unwinding — every call is paused, waiting on the one it made, until the bottom is reached. That's the part that trips people up: the actual arithmetic happens on the way back **up** the stack, not on the way down.

### Why recursion gets slow without help

```python
def fib(n):
    if n <= 1:
        return n
    return fib(n - 1) + fib(n - 2)   # TWO recursive calls, not one
```

`sum_to_n_recursive` makes one recursive call per level — the stack is a straight line. `fib` makes *two* calls per level, and both of those branch into two more — the call tree doubles at every level, and `fib(5)` ends up computing `fib(2)` three separate times with no memory that it already did that work. That repeated-subproblem waste is exactly what today's DSA problem runs into.

## 🧩 DSA — Climbing Stairs *(Easy · Dynamic Programming)*

**NeetCode:** https://neetcode.io/problems/climbing-stairs

### The Problem

You're climbing a staircase with `n` steps. Each move, you can climb either 1 or 2 steps. How many distinct ways can you reach the top?

### Reading the problem like an engineer

Strip the staircase framing: *"how many ways can you build the number `n` out of 1s and 2s, where order matters?"* The number of ways to reach step `n` is the number of ways to reach step `n-1` (then take one final 1-step) plus the number of ways to reach step `n-2` (then take one final 2-step) — every path to the top passes through exactly one of those two steps last. That recurrence — `ways(n) = ways(n-1) + ways(n-2)` — is Fibonacci with different starting numbers, and it inherits the exact same repeated-work problem `fib()` has above.

### Approach 1 — Brute Force Recursion (write this first, always)

```python
def climb_stairs_brute(n):
    if n <= 2:
        return n
    return climb_stairs_brute(n - 1) + climb_stairs_brute(n - 2)
    # Time:  O(2^n) — the call tree doubles at every level
    # Space: O(n) — recursion depth
```

Correct — it directly implements the recurrence — but `climb_stairs_brute(30)` alone makes over a million redundant calls.

### Approach 2 — Bottom-Up DP (the insight)

```python
def climb_stairs(n):
    if n <= 2:
        return n
    prev2, prev1 = 1, 2   # ways to reach step 1, ways to reach step 2
    for _ in range(3, n + 1):
        prev2, prev1 = prev1, prev1 + prev2
    return prev1
    # Time:  O(n) — one pass, no repeated work
    # Space: O(1) — only ever two numbers in flight
```

Instead of recursing *down* from `n` and re-deriving the same small answers over and over, build *up* from the base cases once, keeping only the last two results — everything smaller than that is never needed again.

### Walkthrough on `n = 5`

```
prev2=1 (step 1), prev1=2 (step 2)
step 3: prev2,prev1 = 2, 2+1=3   -> ways(3)=3
step 4: prev2,prev1 = 3, 3+2=5   -> ways(4)=5
step 5: prev2,prev1 = 5, 5+3=8   -> ways(5)=8
return 8
```

### Why bottom-up, specifically

The recursive version re-derives `ways(3)` every time something needs it — once for `ways(5)`'s left branch, again buried inside `ways(4)`'s branch, and so on. Bottom-up DP computes each `ways(k)` exactly once, in order, and only keeps the two values still needed going forward — trading the recursive call tree for a single loop and O(1) memory instead of O(n) stack depth.

## ⚡ FASTAPI — Lifespan Events

### Intuition

Every app so far has done its setup work lazily, inline, the first time it's needed — or not at all. `@asynccontextmanager` lifespan functions give FastAPI a dedicated place to run code exactly once at **startup** (before the app accepts any requests) and exactly once at **shutdown** (after the last request finishes) — the natural home for "warm a cache," "open a DB connection pool," or "load a model into memory," none of which you want repeated on every single request.

### The Essentials

```python
from contextlib import asynccontextmanager
from fastapi import FastAPI

app_state = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    # STARTUP — everything before `yield` runs once, before requests are served
    app_state["stair_cache"] = {n: climb_stairs(n) for n in range(1, 31)}
    print("startup: cache warmed")

    yield   # <- the app runs here, handling requests, until shutdown

    # SHUTDOWN — everything after `yield` runs once, after the last request
    print("shutdown: cleaning up")
    app_state.clear()

app = FastAPI(lifespan=lifespan)
```

The `yield` is the whole mechanism: code before it is startup, code after it is shutdown, and the app serves requests for as long as the generator is paused at the `yield`. `app_state` is a plain dict here for simplicity — the same pattern is how you'd hand a real database connection pool to every route via `request.app.state`.

### Middleware, reused from Day 8

```python
@app.middleware("http")
async def count_requests(request: Request, call_next):
    app_state["request_count"] += 1
    return await call_next(request)
```

Lifespan sets up `app_state` once; middleware (Day 8) touches it on every request. Different lifetimes, same shared dict — this is the first day two separate FastAPI mechanisms cooperate on shared state instead of each owning their own.

## 🔗 COMBINED TASK — Wiring All Three

`lifespan` precomputes `climb_stairs()` for every `n` from 1 to 30 once at startup — reusing today's DP function directly — so `GET /stairs/{n}` is a cache lookup for anything in that range and falls back to computing it live (still O(n), never the O(2^n) brute force) for anything larger. Middleware from Day 8 counts every request into the same `app_state` dict the lifespan hook created, and `StockNotFoundError` from Day 11 continues to flow through its registered handler — showing that yesterday's exception-handling pattern and today's startup pattern coexist in the same app without stepping on each other.

```python
# main.py — Day 12 combined pieces

def climb_stairs(n):
    if n <= 2:
        return n
    prev2, prev1 = 1, 2
    for _ in range(3, n + 1):
        prev2, prev1 = prev1, prev1 + prev2
    return prev1


@asynccontextmanager
async def lifespan(app: FastAPI):
    app_state["stair_cache"] = {n: climb_stairs(n) for n in range(1, 31)}
    app_state["request_count"] = 0
    yield
    app_state.clear()


@app.get("/stairs/{n}")
def stairs(n: int):
    if n not in app_state["stair_cache"]:
        return {"n": n, "ways": climb_stairs(n), "cached": False}
    return {"n": n, "ways": app_state["stair_cache"][n], "cached": True}
```

## 💬 MARCHING ORDERS

Today's thread: recursion is just two rules — a base case and a shrinking recursive case — but naive recursion pays for that simplicity by re-solving the same subproblem over and over, which is exactly the gap between `climb_stairs_brute`'s O(2^n) call tree and `climb_stairs`'s O(n) bottom-up pass. Lifespan events gave FastAPI a real answer to "don't redo expensive work on every request" — precompute once at startup, the same fix in spirit as trading recursion for a loop.

# fastapi/12_lifespan_events/main.py
# Run: uvicorn main:app --reload

from contextlib import asynccontextmanager
from fastapi import FastAPI, Depends, Request, status
from fastapi.responses import JSONResponse
from pydantic import BaseModel
from typing import List

app_state = {}


def climb_stairs(n):
    if n <= 2:
        return n
    prev2, prev1 = 1, 2
    for _ in range(3, n + 1):
        prev2, prev1 = prev1, prev1 + prev2
    return prev1


@asynccontextmanager
async def lifespan(app: FastAPI):
    app_state["stair_cache"] = {n: climb_stairs(n) for n in range(1, 31)}
    app_state["request_count"] = 0
    print("startup: stair_cache warmed for n=1..30")

    yield

    print(f"shutdown: handled {app_state['request_count']} requests")
    app_state.clear()


app = FastAPI(title="Sprint Day 12", lifespan=lifespan)


class StockNotFoundError(Exception):
    def __init__(self, stock_id: int):
        self.stock_id = stock_id


class StockIn(BaseModel):
    ticker: str
    prices: List[int]


stock_db = {}
next_id = 1


def get_stock_or_404(stock_id: int):
    if stock_id not in stock_db:
        raise StockNotFoundError(stock_id)
    return stock_db[stock_id]


@app.exception_handler(StockNotFoundError)
def stock_not_found_handler(request: Request, exc: StockNotFoundError):
    return JSONResponse(
        status_code=status.HTTP_404_NOT_FOUND,
        content={"error": "stock_not_found", "detail": f"stock {exc.stock_id} not found"},
    )


@app.middleware("http")
async def count_requests(request: Request, call_next):
    app_state["request_count"] += 1
    return await call_next(request)


@app.get("/")
def root():
    return {"message": "Sprint Day 12 is running.", "day": 12, "requests_so_far": app_state["request_count"]}


@app.get("/stairs/{n}")
def stairs(n: int):
    if n not in app_state["stair_cache"]:
        return {"n": n, "ways": climb_stairs(n), "cached": False}
    return {"n": n, "ways": app_state["stair_cache"][n], "cached": True}


@app.post("/stocks", status_code=status.HTTP_201_CREATED)
def create_stock(payload: StockIn):
    global next_id
    stock_id = next_id
    stock_db[stock_id] = payload.model_dump()
    next_id += 1
    return {"id": stock_id, **stock_db[stock_id]}


@app.get("/stocks/{stock_id}")
def get_stock(stock_id: int, stock: dict = Depends(get_stock_or_404)):
    return stock

## 🔑 CONCEPT ANSWER

**Question:** "Why does naive recursive Fibonacci take O(2^n) time to compute a result that only has n distinct subproblems?"

**Answer:** `fib(n)` makes two recursive calls — `fib(n-1)` and `fib(n-2)` — and each of *those* makes two more, so the call tree has two branches at every level down to the base cases. A tree that branches in two at every one of its `n` levels has roughly 2^n leaves, so the function makes on the order of 2^n calls total — even though there are only `n` actually distinct subproblems (`fib(0)` through `fib(n)`). The waste is that the tree doesn't know it's solving the same subproblem twice: `fib(5)` calls `fib(3)` once directly and once more buried inside its call to `fib(4)`, and neither call remembers the other happened. Fixing that — storing each `fib(k)` the first time it's computed and looking it up instead of recomputing it — is memoization, tomorrow's topic, and it turns the same recurrence from O(2^n) into O(n).
