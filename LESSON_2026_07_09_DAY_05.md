## 🐍 PYTHON — Control Flow

### Intuition

Every function you've written since Day 1 has had an `if` in it somewhere — checking a key exists, checking a list is empty, checking a price beat the running minimum. Today is about naming that tool properly and picking up two shapes you haven't used yet: the **ternary expression** (an `if/else` that fits in one line, for when you're just choosing a value) and Python's `match` statement (structural pattern matching — a switch statement that can also destructure).

### The Essentials

```python
# if / elif / else — you already know this one
age = 17
if age >= 18:
    status = "adult"
elif age >= 13:
    status = "teen"
else:
    status = "child"

# Ternary expression — an if/else that evaluates to a value, not a block
status = "adult" if age >= 18 else "minor"
label = "even" if age % 2 == 0 else "odd"

# Truthy / falsy — what "if x:" actually checks
# Falsy: 0, 0.0, "", [], {}, set(), None, False
# Everything else is truthy
prices = []
if prices:            # False — empty list is falsy
    print("has prices")
else:
    print("no prices")   # this runs

# match statement (Python 3.10+) — pattern matching, not just value equality
def describe_status_code(code):
    match code:
        case 200 | 201 | 204:
            return "success"
        case 400 | 404 | 422:
            return "client error"
        case 500:
            return "server error"
        case _:
            return "unknown"   # `_` is the wildcard, like `else`

# match can also destructure — this is what makes it more than a switch statement
def describe_point(point):
    match point:
        case (0, 0):
            return "origin"
        case (x, 0):
            return f"on the x-axis at {x}"
        case (0, y):
            return f"on the y-axis at {y}"
        case (x, y):
            return f"at ({x}, {y})"
```

### Why `match` over a chain of `elif`

A long `if/elif/elif/elif` chain checking the same variable against different values works, but `match` says the same thing more directly — "branch on what this value *is* or *looks like*" — and the destructuring form (`case (x, 0):`) does something `elif` genuinely can't do in one line: pull values out of a structure while checking its shape. Reach for `match` when you're branching on a fixed set of known values or shapes; keep `if/elif` when your conditions are open-ended comparisons (`if price < min_price`).

## 🧩 DSA — Valid Palindrome *(Easy · Two Pointers)*

**NeetCode:** https://neetcode.io/problems/valid-palindrome

### The Problem

Given a string, determine if it's a palindrome after converting all uppercase letters to lowercase and removing all non-alphanumeric characters.

### Reading the problem like an engineer

Strip the wrapper: *"Ignoring punctuation and case, does this string read the same forwards and backwards?"* You could clean the string first and then compare it to its reverse — that works, but it's Day 4's instinct (build a new structure, then check it). Today's new tool is **two pointers**: walk one index in from the left and one in from the right at the same time, and stop the instant they disagree. No new string ever gets built.

### Approach 1 — Brute Force (write this first, always)

```python
def is_palindrome_brute(s):
    cleaned = [c.lower() for c in s if c.isalnum()]
    return cleaned == cleaned[::-1]
    # Time:  O(n) — one pass to clean, one to reverse and compare
    # Space: O(n) — the cleaned list and its reverse both live in memory
```

### Approach 2 — Two Pointers (the insight)

```python
def is_palindrome(s):
    left, right = 0, len(s) - 1

    while left < right:
        while left < right and not s[left].isalnum():
            left += 1
        while left < right and not s[right].isalnum():
            right -= 1

        if s[left].lower() != s[right].lower():
            return False

        left += 1
        right -= 1

    return True

    # Time:  O(n) — each pointer crosses the string at most once
    # Space: O(1) — two integers, no copy of the string
```

### Walkthrough on `s = "A man, a plan, a canal: Panama"`

```
left=0 ('A'), right=29 ('a')  -> both alnum, 'a' == 'a' -> match, left=1, right=28
left=1 (' '), not alnum -> left=2 ('m')
right=28 ('m'), alnum -> compare 'm' == 'm' -> match, left=3, right=27
... (this continues inward, skipping every space/comma/colon) ...
-> pointers meet in the middle without ever disagreeing
-> return True
```

### Why two pointers beats the brute force here

The brute force is still O(n) time, so the win isn't asymptotic — it's O(1) space instead of O(n). That's the actual skill today: recognizing when you can answer a "does this match from both ends" question by walking inward instead of materializing a whole new cleaned/reversed copy. This is the first of a whole family of two-pointer problems (Two Sum II, 3Sum, container problems) where the pattern — narrow the window from both sides based on what you compare — repeats with small variations.

    # Swagger now documents this route as returning 201, not 200 —

### What Swagger UI is showing you that you've been skipping

Open `/docs` and look past the "Try it out" button:
- **Schemas** at the bottom of the page show the exact shape of every Pydantic model (`StockIn`, etc.) — this is generated from your `BaseModel` classes, not hand-written.
- Each endpoint lists its **possible response codes** — right now everything says `200`, because that's FastAPI's default when you don't specify one. Setting `status_code=201` on your POST route is the first step toward that list being accurate.
- The `422 Validation Error` response is already there on every route that takes a body — that's automatic the moment you use a Pydantic model, before you write a single line of error-handling code.

We're still not using `HTTPException` yet — manually raising a 404 with a real status code, instead of returning `{"error": "..."}"`, is Day 6's topic. Today is about the codes that FastAPI sets *for* you and the one you can set with a single decorator argument.

## 🔗 COMBINED TASK — Wiring All Three

The two-pointer palindrome check from DSA becomes a new endpoint, and it uses `match` from today's Python block to turn a validation outcome into the right response shape — reinforcing that `match`/`if-else` you just learned by branching on a real result instead of a toy example.

```python
# main.py — Day 5 combined endpoint

@app.get("/stocks/{stock_id}/is-ticker-palindrome", status_code=status.HTTP_200_OK)
def is_ticker_palindrome(stock_id: int):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}

    ticker = stock_db[stock_id]["ticker"]
    result = is_palindrome(ticker)

    # match on the boolean result — small, but it's today's control-flow
    # pattern applied to a real branching decision instead of a toy example
    match result:
        case True:
            verdict = f"'{ticker}' reads the same forwards and backwards."
        case False:
            verdict = f"'{ticker}' is not a palindrome."

    return {"id": stock_id, "ticker": ticker, "is_palindrome": result, "verdict": verdict}
```

# fastapi/05_status_codes/main.py
# Run: uvicorn main:app --reload

from fastapi import FastAPI, status
from pydantic import BaseModel
from typing import List

app = FastAPI(title="Sprint Day 5")


class StockIn(BaseModel):
    ticker: str
    prices: List[int]


stock_db = {}
next_id = 1


def is_palindrome(s):
    left, right = 0, len(s) - 1
    while left < right:
        while left < right and not s[left].isalnum():
            left += 1
        while left < right and not s[right].isalnum():
            right -= 1
        if s[left].lower() != s[right].lower():
            return False
        left += 1
        right -= 1
    return True


@app.get("/")
def root():
    return {"message": "Sprint Day 5 is running.", "day": 5}


@app.get("/stocks")
def list_stocks():
    return stock_db


@app.post("/stocks", status_code=status.HTTP_201_CREATED)
def create_stock(payload: StockIn):
    global next_id
    stock_id = next_id
    stock_db[stock_id] = payload.model_dump()
    next_id += 1
    return {"id": stock_id, **stock_db[stock_id]}


@app.put("/stocks/{stock_id}")
def update_stock(stock_id: int, payload: StockIn):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}
    stock_db[stock_id] = payload.model_dump()
    return {"id": stock_id, **stock_db[stock_id]}


@app.delete("/stocks/{stock_id}", status_code=status.HTTP_200_OK)
def delete_stock(stock_id: int):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}
    removed = stock_db.pop(stock_id)
    return {"deleted_id": stock_id, "ticker": removed["ticker"]}


@app.get("/stocks/{stock_id}/max-profit")
def stock_max_profit(stock_id: int):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}

    prices = stock_db[stock_id]["prices"]
    min_price = prices[0] if prices else 0
    best_profit = 0
    for price in prices[1:]:
        if price < min_price:
            min_price = price
        else:
            best_profit = max(best_profit, price - min_price)

    return {"id": stock_id, "ticker": stock_db[stock_id]["ticker"], "max_profit": best_profit}


@app.get("/stocks/{stock_id}/is-ticker-palindrome", status_code=status.HTTP_200_OK)
def is_ticker_palindrome(stock_id: int):

## 🔑 CONCEPT ANSWER

**Question:** "Is `0` truthy or falsy in Python, and why does that matter when checking `if count:` versus `if count is not None:`?"

**Answer:** `0` is falsy — it's one of Python's built-in falsy values alongside `""`, `[]`, `{}`, and `None`. That matters because `if count:` and `if count is not None:` mean different things the moment `count` can legitimately be `0`: `if count:` treats a real, valid zero the same as "missing," so code tracking something like an item count or a page number will silently skip the zero case. `if count is not None:` only excludes the actual absence of a value, so a genuine `0` still passes through. The rule of thumb: use `if x:` when any falsy value (including `0`, `""`, `[]`) should be treated as "nothing to do here," and use `if x is not None:` when zero, empty string, or empty list are valid data you still need to act on.
