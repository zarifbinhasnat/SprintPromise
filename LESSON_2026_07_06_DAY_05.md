## 🐍 PYTHON — Control Flow: Branching, Ternaries, `match`, and Truthiness

### Intuition

Every program you've written this week already has branching (`if stock_id not in stock_db`), but today formalizes the tools: `if/elif/else` for multi-way branches, the ternary expression for a branch that's really just picking a value, `match` for branching on shape/structure rather than one condition at a time, and truthy/falsy for the values Python treats as "empty" without you writing `== 0` or `== ""` explicitly.

### The Essentials

```python
# if / elif / else — evaluated top to bottom, first True branch wins, rest skipped
score = 72
if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
elif score >= 70:
    grade = "C"
else:
    grade = "F"

# Ternary expression — a branch that only picks a VALUE, not a block of statements
n = 7
label = "even" if n % 2 == 0 else "odd"     # "odd"

# match statement (3.10+) — branch on the SHAPE of a value, not just equality
def describe(command):
    match command.split():
        case ["go", direction]:
            return f"moving {direction}"
        case ["stop"]:
            return "stopping"
        case [action, *rest] if action == "set":
            return f"setting {rest}"
        case _:
            return "unknown command"

describe("go north")   # "moving north"
describe("stop")       # "stopping"
```

### Truthy / falsy — the values Python treats as "empty"

```python
# Falsy: 0, 0.0, "", [], {}, set(), None, False
# Everything else is truthy — including "0" (non-empty string!) and [0] (non-empty list)

prices = []
if prices:              # False — empty list is falsy
    print("has prices")
else:
    print("no prices yet")

# This is why Day 4's stock_max_profit could have written:
#   if not prices: return 0
# instead of
#   if len(prices) == 0: return 0
# — they're equivalent, but the truthy check is the idiom.
```

### `if x:` vs. `if x is not None:` — where they actually diverge

```python
def show_count(count):
    if count:              # False for BOTH count=None and count=0
        print(f"count: {count}")
    else:
        print("nothing to show")

show_count(0)   # prints "nothing to show" — but 0 might be a legitimate count!

def show_count_fixed(count):
    if count is not None:   # only False for None — 0 is a valid, printable value
        print(f"count: {count}")
    else:
        print("nothing to show")

show_count_fixed(0)   # prints "count: 0" — correct
```

This is the bug worth internalizing: `if x:` silently treats `0`, `""`, and `[]` the same as `None`. Use plain truthy checks when "empty and missing are the same case" (Day 4's `prices` check above), and use `is not None` the moment a valid falsy value (like `0`) must be distinguished from "not provided."

## 🧩 DSA — Valid Palindrome *(Easy · Two Pointers)*

**NeetCode:** https://neetcode.io/problems/valid-palindrome

### The Problem

Given a string `s`, return `True` if it reads the same forward and backward after (1) converting all letters to lowercase and (2) removing all non-alphanumeric characters.

### Reading the problem like an engineer

Every problem so far this week reached for a hash structure — a set to check "seen," a dict to count. Valid Palindrome is the first one where a hash structure buys you nothing, because the question isn't "have I seen this" — it's "does the first character match the last, the second match the second-to-last," and so on, working inward. That's a job for **two pointers**, one starting at each end.

### Approach 1 — Brute Force (write this first, always)

```python
def is_palindrome_brute(s):
    filtered = "".join(c.lower() for c in s if c.isalnum())
    return filtered == filtered[::-1]
    # Time:  O(n) — one pass to filter, one to reverse and compare
    # Space: O(n) — the filtered string and its reverse are new strings
```

### Approach 2 — Two Pointers, In Place (the insight)

```python
def is_palindrome(s):
    left, right = 0, len(s) - 1
    while left < right:
        while left < right and not s[left].isalnum():
            left += 1
        while left < right and not s[right].isalnum():
            right -= 1
        if s[left].lower() != s[right].lower():
            return False
        left += 1
        right -= 1
    return True

    # Time:  O(n) — each pointer moves inward, never backward
    # Space: O(1) — no new string is ever built
```

### Walkthrough on `s = "A man, a plan, a canal: Panama"`

```
left=0 ('A'), right=29 ('a')  -> 'a' == 'a'  -> move both inward
left=1 (' '), skip non-alnum -> left=2 ('m')
right=28 ('m')                -> 'm' == 'm'  -> move both inward
... continues inward, every pair matches ...
left meets right -> return True
```

### Why this is the pattern shift Day 4 promised

Approach 1 is what Day 1–4 trained you to reach for by default: transform the data, then compare. Approach 2 is strictly better *and* uses no hash structure at all — it exploits the fact that a palindrome check only ever needs to compare symmetric positions, so you never need to store anything, just two indices closing in on each other. Recognizing "this is a from-both-ends problem" is the actual skill; the two-pointer template itself is only a few lines.

## ⚡ FASTAPI — Swagger UI Deep Dive, Response Status Codes & Week 1 Review

### Intuition

Every endpoint you've built since Day 1 has been visible at `/docs`, but so far it's shown up there by accident — FastAPI auto-generates it from your function signatures. Today you drive that page on purpose: `response_model` locks down and documents your output shape, `status_code` tells the client (and the docs) what a successful call actually returns, and `tags`/`summary` organize `/docs` into readable sections instead of one long list.

### The Essentials

```python
from fastapi import FastAPI, status
from pydantic import BaseModel

app = FastAPI(title="Sprint Day 5")

class PalindromeIn(BaseModel):
    text: str

class PalindromeOut(BaseModel):
    text: str
    is_palindrome: bool
    verdict: str

@app.post(
    "/palindrome-check",
    response_model=PalindromeOut,      # locks the documented + validated output shape
    status_code=status.HTTP_200_OK,    # explicit instead of FastAPI's implicit 200 default
    tags=["DSA Demos"],                # groups this endpoint under "DSA Demos" in /docs
    summary="Check whether a string is a valid palindrome",
)
def palindrome_check(payload: PalindromeIn):
    ...
```

### Why `response_model` matters beyond documentation

Without it, FastAPI just serializes whatever your function returns — a typo'd key or an extra internal field ships straight to the client. With `response_model=PalindromeOut`, FastAPI **validates and filters** the return value against that shape before sending it, so `/docs` shows the true contract and a mismatch fails loudly instead of leaking silently.

### `status_code` — matching the verb (a preview of Day 6's `HTTPException`)

```python

#   GET / PUT / DELETE that succeeds -> 200 OK
# We're still returning {"error": "..."} dicts for the not-found case (from Day 4) —
# proper HTTPException(status_code=404, ...) that actually sets the HTTP status is Day 6's topic.
```

## 🔗 COMBINED TASK — Wiring All Three

The ternary from today's Python block (`"palindrome" if result else "not a palindrome"`) turns the two-pointer boolean from Valid Palindrome into a human-readable verdict, and `response_model` + explicit `status_code` from today's FastAPI block document that exact shape in `/docs`.

```python
# main.py — Day 5 combined endpoint

def is_palindrome(s: str) -> bool:
    left, right = 0, len(s) - 1
    while left < right:
        while left < right and not s[left].isalnum():
            left += 1
        while left < right and not s[right].isalnum():
            right -= 1
        if s[left].lower() != s[right].lower():
            return False
        left += 1
        right -= 1
    return True


@app.post(
    "/palindrome-check",
    response_model=PalindromeOut,
    status_code=status.HTTP_200_OK,
    tags=["DSA Demos"],
    summary="Check whether a string is a valid palindrome",
)
def palindrome_check(payload: PalindromeIn):
    result = is_palindrome(payload.text)
    verdict = "palindrome" if result else "not a palindrome"   # today's ternary, applied
    return PalindromeOut(text=payload.text, is_palindrome=result, verdict=verdict)
```

## 🔑 CONCEPT ANSWER

**Question:** "Why does `if count:` behave differently from `if count is not None:`, and when does that difference actually cause a bug?"

**Answer:** `if count:` asks "is this value truthy?" — and in Python, `0` is falsy, exactly like `None`, `""`, and `[]`. `if count is not None:` asks a completely different question: "was a value actually provided?" — and `0` answers that question as *yes*. The two checks agree for every value except the falsy-but-meaningful ones (`0`, `""`, `[]`, `False`). The bug shows up anywhere zero is a legitimate result you still need to display or process — a stock count of `0`, a score of `0`, an empty-but-valid API response — because `if count:` silently treats "the real value is zero" the same as "nothing was passed in at all," dropping a valid `0` into the same branch as a missing value.
