## 🐍 PYTHON — Control Flow

### Intuition

Every program you've written since Day 1 has been "run these lines in order." Control flow is how you make a program *decide* — branch on a condition, pick between two values in one expression, or match a value's exact shape. `if/elif/else` you've already used without naming it; today you make it explicit and add two tools that make branching more expressive: the ternary expression and `match`.

### The Essentials

```python
# if / elif / else — order matters, first true branch wins
score = 82
if score >= 90:
    grade = "A"
elif score >= 80:
    grade = "B"
else:
    grade = "F"

# Ternary expression — an if/else that returns a value, written in one line
parity = "even" if n % 2 == 0 else "odd"

# match — structural pattern matching (Python 3.10+)
# Best when you're comparing one value against many discrete cases
match status_code:
    case 200 | 201 | 204:
        result = "success"
    case 400 | 401 | 403 | 404:
        result = "client error"
    case _:
        result = "unknown"          # the wildcard — always needed as a fallback
```

### Truthy / Falsy

```python
# Every value has a boolean identity, not just True/False
bool(0)    # False        bool(1)    # True
bool("")   # False        bool("x")  # True
bool([])   # False        bool([1])  # True
bool({})   # False        bool(None) # False

if not stock_db:      # idiomatic "is this empty?" — no len() needed
    print("empty")
```

### Why it matters going forward

`match` isn't just a fancier `if/elif` chain — notice `case 200 | 201 | 204` groups multiple values into one branch, which is exactly the shape you need today for turning an HTTP status code into a category. And truthy/falsy is why `if stock_id not in stock_db` and `if not stock_db` both read naturally — Python treats "missing" and "empty" as the same kind of false.

## 🧩 DSA — Valid Palindrome *(Easy · Two Pointers)*

**NeetCode:** https://neetcode.io/problems/valid-palindrome

### The Problem

Given a string `s`, return `True` if it reads the same forwards and backwards once you lowercase it and strip out everything that isn't a letter or digit.

### Reading the problem like an engineer

The brute-force read is "clean the string, then compare it to its reverse" — one pass to clean, one comparison, done, but it costs a full extra copy of the string. The two-pointer read asks a sharper question: *do I actually need a cleaned copy, or can I just walk in from both ends and skip the junk as I go?* This is your first pattern this week that isn't a hash lookup (Days 1–4 were all dicts/sets) — it's positional, using two indices instead of a container.

### Approach 1 — Brute Force (write this first, always)

```python
def is_palindrome_brute(s):
    cleaned = [ch.lower() for ch in s if ch.isalnum()]
    return cleaned == cleaned[::-1]
    # Time:  O(n) — one pass to clean, one to reverse/compare
    # Space: O(n) — the cleaned list is a full copy
```

### Approach 2 — Two Pointers (the insight)

```python
def is_palindrome(s):
    left, right = 0, len(s) - 1
    while left < right:
        while left < right and not s[left].isalnum():
            left += 1
        while left < right and not s[right].isalnum():
            right -= 1
        if s[left].lower() != s[right].lower():
            return False
        left += 1
        right -= 1
    return True

    # Time:  O(n) — each pointer moves forward at most n times total
    # Space: O(1) — two integers, no copy of the string
```

### Walkthrough on `s = "0P"`

```
left=0 ('0'), right=1 ('P')
'0'.isalnum() -> True, 'P'.isalnum() -> True, no skipping
'0'.lower() = '0', 'P'.lower() = 'p'  -> '0' != 'p'
-> return False
```

Same O(n) time as the brute force, but O(1) space instead of O(n) — the real lesson of two pointers is trading a data structure for two indices that do the same job.

### Why the two-pointer approach works

Non-alphanumeric characters carry no information about whether the string is a palindrome, so skipping them with the inner `while` loops is free — it doesn't change the answer, only where you're looking. Comparing from both ends inward means the moment any pair of "real" characters disagrees, you can stop immediately; if the pointers meet or cross without ever disagreeing, every pair matched, so it must be a palindrome.

### The status codes that matter this week

| Code | Meaning | When to use it |
|------|---------|-----------------|
| 200 OK | Success, returning data | GET, PUT |
| 201 Created | Success, new resource made | POST |
| 204 No Content | Success, nothing to return | DELETE |
| 404 Not Found | Resource doesn't exist | *(proper version lands Day 6 via `HTTPException`)* |

## 🔑 CONCEPT ANSWER

**Question:** "When would you reach for `match` instead of a chain of `if/elif`?"

**Answer:** Reach for `match` when you're comparing one value against several *discrete, known* cases — especially when some of those cases naturally group together (`case 200 | 201 | 204:`) or when you want to destructure a value's shape (`case (x, 0):` to pull out a coordinate). An `if/elif` chain is the better fit when your conditions are ranges or open-ended comparisons (`score >= 90`), since `match` compares against fixed patterns rather than arbitrary boolean expressions. In short: `match` for "which exact case is this," `if/elif` for "which range or condition is true."
