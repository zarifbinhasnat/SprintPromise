## 🐍 PYTHON — *args and **kwargs

### Intuition

Sometimes a function needs to accept "however many arguments the caller wants to give" — `*args` collects extra positional arguments into a tuple, `**kwargs` collects extra keyword arguments into a dict. You've been a *user* of this since Day 1 every time you called `print(a, b, c)` — `print` itself is defined with `*args`.

### The Essentials

```python
# *args — variable positional arguments, collected as a tuple
def total(*args):
    return sum(args)

total(1, 2, 3)        # 6
total(1, 2, 3, 4, 5)   # 15

# **kwargs — variable keyword arguments, collected as a dict
def build_stock(**kwargs):
    return kwargs

build_stock(ticker="AAA", price=10)
# {'ticker': 'AAA', 'price': 10}

# Combining fixed params, *args, and **kwargs — this is the real-world order
def log_call(action, *args, **kwargs):
    print(f"{action} called with args={args}, kwargs={kwargs}")

log_call("create_stock", "AAA", 10, active=True)
# create_stock called with args=('AAA', 10), kwargs={'active': True}

# Unpacking — the reverse direction: spreading a list/dict INTO a call
def create_stock(ticker, price):
    return {"ticker": ticker, "price": price}

args = ["AAA", 10]
create_stock(*args)              # same as create_stock("AAA", 10)

kwargs = {"ticker": "AAA", "price": 10}
create_stock(**kwargs)           # same as create_stock(ticker="AAA", price=10)
```

### Why this matters for the FastAPI you already know

Every decorator you've used since Day 1 — `@app.get("/stocks/{stock_id}")` — is a function that takes your endpoint function and wraps it. Wrapping code that needs to work with *any* endpoint, no matter its own parameters, is written with `*args, **kwargs`:

```python
def log_wrapper(func):
    def wrapper(*args, **kwargs):
        print(f"calling {func.__name__}")
        return func(*args, **kwargs)   # forward whatever was actually passed in
    return wrapper
```

This is exactly the shape today's FastAPI middleware needs — code that has to work no matter what request comes through.

## 🧩 DSA — Maximum Subarray *(Easy · Arrays, Kadane's Algorithm)*

**NeetCode:** https://neetcode.io/problems/maximum-subarray

### The Problem

Given an integer array `nums`, find the contiguous subarray with the largest sum, and return that sum.

### Reading the problem like an engineer

Strip the wrapper: *"As I walk through the array, is it worth carrying my running sum forward, or would I do better starting fresh from here?"* That's Day 4's running-tracker idea again — but instead of tracking a minimum, you're tracking a running sum, and deciding at every step whether the past is still helping you or actively hurting you.

### Approach 1 — Brute Force (write this first, always)

```python
def max_subarray_brute(nums):
    best = nums[0]
    for i in range(len(nums)):
        current_sum = 0
        for j in range(i, len(nums)):
            current_sum += nums[j]
            best = max(best, current_sum)
    return best
    # Time:  O(n²) — every subarray's sum computed
    # Space: O(1)
```

### Approach 2 — Kadane's Algorithm (the insight)

```python
def max_subarray(nums):
    best = nums[0]
    current = 0
    for n in nums:
        if current < 0:
            current = 0        # the running sum is dragging us down — drop it
        current += n
        best = max(best, current)
    return best

    # Time:  O(n) — one pass
    # Space: O(1) — two running variables
```

### Walkthrough on `nums = [-2, 1, -3, 4, -1, 2, 1, -5, 4]`

```
current=0, best=-2
n=-2 -> current not <0 (it's ==0) -> current=-2 -> best=max(-2,-2)=-2
n=1  -> current=-2 <0 -> reset to 0 -> current=0+1=1 -> best=max(-2,1)=1
n=-3 -> current=1, not<0 -> current=1-3=-2 -> best stays 1
n=4  -> current=-2<0 -> reset -> current=0+4=4 -> best=4
n=-1 -> current=4-1=3 -> best=4
n=2  -> current=3+2=5 -> best=5
n=1  -> current=5+1=6 -> best=6
n=-5 -> current=6-5=1 -> best=6
n=4  -> current=1+4=5 -> best=6
-> return 6   (subarray [4, -1, 2, 1])
```

### Why the reset works

If the running sum ever goes negative, it can only ever *hurt* any subarray that includes it — so the best move is to abandon it and start counting fresh from the next element. This is the same "the running tracker only carries forward what's still useful" idea from Day 4's min-price tracker, applied to a sum instead of a minimum: at every position you ask "is my past worth keeping," not "what was my past."

## ⚡ FASTAPI — Middleware

### Intuition

Everything you've written so far runs *inside* one endpoint. Middleware runs *around every request*, before your route function and after it — the natural place for logging, timing, or CORS headers, and exactly the "works no matter what the endpoint's own signature looks like" problem `*args`/`**kwargs` solve.

### The Essentials

```python
from fastapi import FastAPI, Request
import time

app = FastAPI()

@app.middleware("http")
async def log_requests(request: Request, call_next):
    start = time.time()
    response = await call_next(request)   # runs the actual endpoint
    duration = time.time() - start
    print(f"{request.method} {request.url.path} -> {response.status_code} ({duration:.3f}s)")
    return response
```

### CORS — the middleware you'll use in almost every real project

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],   # which frontends may call this API
    allow_methods=["*"],
    allow_headers=["*"],
)
```

Without CORS middleware, a browser-based frontend running on a different origin (like `localhost:3000` calling an API on `localhost:8000`) gets silently blocked by the browser — not by FastAPI. This is the single most common "why does my frontend get a network error but Postman works fine" bug, and it's a one-time middleware setup, not something you fix per-endpoint.

## 🔗 COMBINED TASK — Wiring All Three

`max_subarray` (today's Kadane's walk) becomes an endpoint answering "what's the best contiguous run of price changes for this stock," and the logging middleware wraps every call — including this new one — using the `*args, **kwargs`-shaped `call_next` pattern from today's Python block.

```python
# main.py — Day 8 combined endpoint

def max_subarray(nums):
    best = nums[0]
    current = 0
    for n in nums:
        if current < 0:
            current = 0
        current += n
        best = max(best, current)
    return best


@app.get("/stocks/{stock_id}/best-run")
def stock_best_run(stock_id: int):
    if stock_id not in stock_db:
        raise HTTPException(status_code=404, detail=f"stock {stock_id} not found")

    prices = stock_db[stock_id]["prices"]
    if len(prices) < 2:
        return {"id": stock_id, "best_run_sum": 0}

    # day-over-day changes, not raw prices — this is what "best contiguous run" means here
    changes = [prices[i] - prices[i - 1] for i in range(1, len(prices))]
    return {"id": stock_id, "ticker": stock_db[stock_id]["ticker"], "best_run_sum": max_subarray(changes)}
```

## 🔑 CONCEPT ANSWER

**Question:** "Why must `*args` come before `**kwargs` in a function signature, and why must both come after the named parameters?"

**Answer:** Python resolves function arguments in a fixed order — positional first, then variable-positional, then keyword-only, then variable-keyword — because that mirrors how a call is actually parsed: positional arguments fill named parameters left to right, anything extra positional falls into `*args`, and anything passed by name that isn't an explicit parameter falls into `**kwargs`. If `**kwargs` could come before `*args`, Python wouldn't know whether a bare value showing up next was meant to be an extra positional argument or the start of keyword arguments — the ordering removes that ambiguity by construction. Named parameters must come first because they're the ones the caller can supply positionally by matching order; only once those are accounted for does it make sense to ask "what's left over," which is the entire job of `*args` and `**kwargs`.
