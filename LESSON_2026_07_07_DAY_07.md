## 🐍 PYTHON — Functions

### Intuition

A function is a name for "do this sequence of steps, possibly with different inputs each time." The three things that make functions genuinely reusable instead of copy-pasted blocks: **parameters** (what varies), **default arguments** (sensible fallbacks so callers don't have to specify everything), and a clear **return value** (what the caller actually gets back).

### The Essentials

```python
# Basic function — parameters, return value
def max_profit(prices):
    if not prices:
        return 0
    min_price = prices[0]
    best = 0
    for price in prices[1:]:
        if price < min_price:
            min_price = price
        else:
            best = max(best, price - min_price)
    return best

# Default arguments — a fallback the caller can override
def greet(name, greeting="Hello"):
    return f"{greeting}, {name}!"

greet("Amina")                 # "Hello, Amina!"
greet("Yusuf", greeting="Hi")  # "Hi, Yusuf!"

# Keyword arguments — call by name instead of position, for clarity
def create_stock(ticker, prices, active=True):
    return {"ticker": ticker, "prices": prices, "active": active}

create_stock(ticker="AAA", prices=[1, 2, 3])   # order doesn't matter with keywords

# Multiple return values — Python returns a tuple, unpacked automatically
def min_max(nums):
    return min(nums), max(nums)

lo, hi = min_max([3, 1, 4, 1, 5])   # lo=1, hi=5

# Docstrings — the standard way to document what a function does
def is_palindrome(s):
    """Return True if s reads the same forwards and backwards, ignoring case and punctuation."""
    ...
```

### The mutable default argument trap

```python
# DON'T do this:
def add_ticker(ticker, seen=[]):   # the list is created ONCE, at function definition time
    seen.append(ticker)
    return seen

add_ticker("AAA")   # ["AAA"]
add_ticker("BBB")   # ["AAA", "BBB"]  <- surprise! same list every call

# DO this instead:
def add_ticker(ticker, seen=None):
    if seen is None:
        seen = []
    seen.append(ticker)
    return seen
```

This is the single most common Python interview gotcha involving functions — a default argument is evaluated once, when the `def` line runs, not fresh on every call. Mutable defaults (`[]`, `{}`, `set()`) silently share state across calls; `None` as a sentinel, checked with `if x is None:` (today's `is not None` idea from Day 5), is the fix.

## 🧩 DSA — Reverse String *(Easy · Two Pointers)*

**LeetCode:** https://leetcode.com/problems/reverse-string/

### The Problem

Reverse a string in place — given as a list of characters, `s`. You must modify the input in place with O(1) extra memory.

### Reading the problem like an engineer

Strip the wrapper: this is Day 5's two-pointer skill, applied to *mutating* instead of just *comparing*. Walk a `left` pointer in from the start and a `right` pointer in from the end, and swap what they're pointing at each step.

### Approach 1 — Brute Force (write this first, always)

```python
def reverse_string_brute(s):
    reversed_copy = s[::-1]
    for i in range(len(s)):
        s[i] = reversed_copy[i]
    # Time:  O(n)
    # Space: O(n) — reversed_copy is a full second list, which violates the O(1) constraint
```

### Approach 2 — Two Pointers In-Place (the insight)

```python
def reverse_string(s):
    left, right = 0, len(s) - 1
    while left < right:
        s[left], s[right] = s[right], s[left]
        left += 1
        right -= 1
    # Time:  O(n) — n/2 swaps
    # Space: O(1) — two integers, swaps happen in the original list
```

### Walkthrough on `s = ['h', 'e', 'l', 'l', 'o']`

```
left=0, right=4 -> swap 'h','o' -> ['o','e','l','l','h']   left=1, right=3
left=1, right=3 -> swap 'e','l' -> ['o','l','l','e','h']   left=2, right=2
left=2 == right=2 -> loop ends (left < right is False)
-> ['o','l','l','e','h']
```

### Why this belongs in the two-pointer family from Day 5

Day 5's Valid Palindrome walked two pointers inward to *compare*; today walks two pointers inward to *swap*. Same shape, different action at each step — recognizing "this is the two-pointer pattern again, just doing something else at each position" is exactly the kind of pattern-matching that speeds up recognizing new problems as variations of ones you've already solved.

## ⚡ FASTAPI — Response Models

### Intuition

Every endpoint so far has returned whatever dict you built by hand. `response_model=` does two things: it validates and filters what actually goes out (so extra/internal fields never leak to the client), and it documents the exact output shape in Swagger — separate from the input shape.

### The Essentials

```python
from fastapi import FastAPI
from pydantic import BaseModel
from typing import List

app = FastAPI()

class StockIn(BaseModel):
    ticker: str
    prices: List[int]
    internal_notes: str = ""   # something you never want to expose back out

class StockOut(BaseModel):
    id: int
    ticker: str
    prices: List[int]
    # internal_notes is deliberately NOT listed here

stock_db = {}
next_id = 1

@app.post("/stocks", response_model=StockOut, status_code=201)
def create_stock(payload: StockIn):
    global next_id
    stock_id = next_id
    stock_db[stock_id] = payload.model_dump()
    next_id += 1
    # even though the stored dict still has internal_notes, response_model
    # strips it before the response goes out — filtering happens automatically
    return {"id": stock_id, **stock_db[stock_id]}
```

### Why a separate output model matters

`StockIn` is "what the client is allowed to send me." `StockOut` is "what I'm willing to show back." Those are not always the same shape — a password hash, an internal note, a soft-delete flag are all things you might store but never want to leak back through an API response. Without `response_model`, whatever dict your function returns goes out verbatim; with it, FastAPI validates the return value against `StockOut` and drops anything that model doesn't declare.

## 🔗 COMBINED TASK — Wiring All Three

`reverse_string()` becomes an endpoint that reverses a ticker (using today's in-place two-pointer swap), and the response is shaped by a dedicated `TickerReverseOut` model — reinforcing that output shape is a deliberate choice, not just "whatever the function returns."

```python
# main.py — Day 7 combined endpoint

class TickerReverseOut(BaseModel):
    id: int
    original: str
    reversed: str


def reverse_string(chars):
    left, right = 0, len(chars) - 1
    while left < right:
        chars[left], chars[right] = chars[right], chars[left]
        left += 1
        right -= 1


@app.get("/stocks/{stock_id}/reverse-ticker", response_model=TickerReverseOut)
def reverse_ticker(stock_id: int):
    if stock_id not in stock_db:
        raise HTTPException(status_code=404, detail=f"stock {stock_id} not found")

    ticker = stock_db[stock_id]["ticker"]
    chars = list(ticker)
    reverse_string(chars)

    return {"id": stock_id, "original": ticker, "reversed": "".join(chars)}
```

      no internal_notes field, even if you send one in the request

## 🔑 CONCEPT ANSWER

**Question:** "Why does `def add_ticker(ticker, seen=[])` cause a bug that only shows up after the function has already been called once?"

**Answer:** Default argument values in Python are evaluated exactly once, at the moment the `def` statement runs — not freshly on every call. `seen=[]` creates one list object when the function is defined, and every call that doesn't pass its own `seen` argument reuses that *same* list. The first call looks fine (`["AAA"]`), which is why the bug hides — it only becomes visible on the second call, when `"BBB"` gets appended to the list left over from the first call, producing `["AAA", "BBB"]` instead of the expected `["BBB"]`. The fix is to default to `None` (an immutable sentinel) and create a fresh mutable object inside the function body with `if seen is None: seen = []` — this guarantees every call that doesn't pass its own list gets a brand-new one instead of a shared one.
