## 🐍 PYTHON — Control Flow: if/elif/else, Ternary, match, Truthy/Falsy

### Intuition

You've been writing `if`/`else` since Day 1 without thinking about it — today makes the rest of the toolbox explicit: the ternary expression for one-line conditionals, `match` for choosing between several known shapes of a value, and truthy/falsy for why `if prices:` already works without ever needing `if len(prices) > 0:`.

### The Essentials

```python
# Truthy/falsy — empty containers and 0/None are falsy, everything else truthy
if prices:              # same as `if len(prices) > 0`
    print("non-empty")

bool([]), bool({}), bool(""), bool(0), bool(None)   # all False
bool([0]), bool("0"), bool(-1)                       # all True — non-empty/non-zero

# Ternary expression — a one-line if/else that returns a value
verdict = "profitable" if best_profit > 0 else "no profit"

# if/elif/else chain — still the right tool for ordered range checks
def profit_tier(profit):
    if profit <= 0:
        return "loss"
    elif profit < 5:
        return "small win"
    else:
        return "big win"

# match — pattern matching against known, discrete cases (Python 3.10+)
def describe_tier(tier):
    match tier:
        case "loss":
            return "sell at a loss or break even"
        case "small win":
            return "modest gain"
        case "big win":
            return "strong gain"
        case _:                      # wildcard — always include a default
            return "unknown tier"
```

### `match` vs. `if/elif` — when each wins

`if/elif/else` wins for **ranges and conditions** (`profit < 5`, `x > 0`) because `match` compares against fixed patterns, not arbitrary boolean expressions. `match` wins once you're branching on a **known, finite set of exact values or shapes** — a string tier, a status code, a tuple you're destructuring — because every case reads as a flat list instead of a staircase of `elif`s, and the `case _:` wildcard forces you to think about the default.

### Why it matters going forward

`profit_tier()` returns one of three exact strings, and `describe_tier()` branches on exactly that finite set — that's the shape `match` is built for. Today's FastAPI block reuses precisely this: a two-pointer palindrome check returns `True`/`False`, and a `match` turns that boolean into a human-readable verdict in the response.

## 🧩 DSA — Valid Palindrome *(Easy · Two Pointers)*

**NeetCode:** https://neetcode.io/problems/valid-palindrome

### The Problem

Given a string `s`, return `True` if it's a palindrome once you consider only alphanumeric characters and ignore case — `False` otherwise.

### Reading the problem like an engineer

Every DSA day so far has reached for a hash structure (a seen-set, a frequency dict). This problem doesn't need one: a palindrome is symmetric around its center, so the natural check is "does the first character match the last, the second match the second-to-last, and so on?" That's two pointers walking toward each other from opposite ends — the first pattern this sprint that isn't hash-based.

### Approach 1 — Brute Force (write this first, always)

```python
def is_palindrome_brute(s):
    cleaned = [ch.lower() for ch in s if ch.isalnum()]
    return cleaned == cleaned[::-1]
    # Time:  O(n) — one pass to clean, one to reverse-compare
    # Space: O(n) — the cleaned copy is a whole new list
```

### Approach 2 — Two-Pointer (the insight)

```python
def is_palindrome(s):
    left, right = 0, len(s) - 1
    while left < right:
        while left < right and not s[left].isalnum():
            left += 1
        while left < right and not s[right].isalnum():
            right -= 1

        if s[left].lower() != s[right].lower():
            return False

        left += 1
        right -= 1

    return True

    # Time:  O(n) — each pointer crosses the string once, total
    # Space: O(1) — no cleaned copy, just two index variables
```

### Walkthrough on `s = "A man, a plan, a canal: Panama"`

```
left=0 ('A'), right=30 ('a')  -> 'a' == 'a' -> match, move in
left=1 (' '), skip to left=2 ('m')
right=29 ('m')                -> 'm' == 'm' -> match, move in
... continues inward, skipping every space/comma/colon ...
-> pointers cross having matched every pair -> return True
```

### Why the two-pointer approach works

A palindrome is defined by a symmetric relationship between positions `i` and `len(s)-1-i` — there's no need to store anything about characters you've already checked, because each pair is checked exactly once and never revisited. That's what makes O(1) space possible here where Day 3's Contains Duplicate and Day 4's stock problem both needed O(n) auxiliary space (a set) or at minimum a running variable per position — the palindrome check needs *nothing* carried forward except two indices.

### Intuition

You've had `/docs` open since Day 1 without really touring it. Today's the review day: look at what Swagger UI, ReDoc, and the raw OpenAPI schema actually give you, and start naming success status codes on purpose instead of letting everything default to `200`.


### What Swagger UI is actually showing you

Every route you've written since Day 1 — the path, the parameters, the Pydantic request body schema, the response — got turned into the OpenAPI JSON schema automatically, and Swagger UI is just a renderer for that schema with a "Try it out" button wired to real requests. That's why `title`/`description` on `FastAPI(...)` and the type hints on your path/query params and Pydantic models aren't just cosmetic — they're the actual source of what appears in `/docs`. ReDoc renders the identical schema, just optimized for reading over trying.

### Naming success codes on purpose

A plain `return {...}` defaults to `200 OK` — correct for a `GET`, but a bit sloppy for a `POST` that just created something. Passing `status_code=status.HTTP_201_CREATED` to the route decorator makes the Swagger docs (and any client reading the response) tell the truth about what happened. We're still keeping *error* responses as plain dicts today — proper `404`s via `HTTPException` are Day 6's topic, once error handling gets a dedicated block instead of a footnote.

## 🔗 COMBINED TASK — Wiring All Three

The two-pointer walk from DSA runs inside a FastAPI route, and a `match` statement (today's Python block) turns its boolean result into a verdict string.

```python
# main.py — Day 5 combined endpoint

@app.get("/check-ticker-palindrome/{ticker}")
def check_ticker_palindrome(ticker: str):
    left, right = 0, len(ticker) - 1
    is_palindrome = True
    while left < right:
        while left < right and not ticker[left].isalnum():
            left += 1
        while left < right and not ticker[right].isalnum():
            right -= 1
        if ticker[left].lower() != ticker[right].lower():
            is_palindrome = False
            break
        left += 1
        right -= 1

    match is_palindrome:
        case True:
            verdict = "palindrome"
        case False:
            verdict = "not a palindrome"

    return {"ticker": ticker, "is_palindrome": is_palindrome, "verdict": verdict}
```

## 🔑 CONCEPT ANSWER

**Question:** "Why is `if some_list:` preferred over `if len(some_list) > 0:` in Python?"

**Answer:** Every built-in container defines truthiness as "empty is falsy, non-empty is truthy" — `bool([])` is `False`, `bool([0])` is `True` regardless of what's inside. `if some_list:` asks that question directly and reads the way you'd say it out loud ("if there are prices"), while `if len(some_list) > 0:` computes a length just to compare it to zero, which is strictly more work for the same answer. The one place `len(...)` still earns its keep is when you need the actual count for something else afterward (a message, a loop bound) — if all you need is "is this empty or not," truthiness is the idiomatic Python way to ask it.
