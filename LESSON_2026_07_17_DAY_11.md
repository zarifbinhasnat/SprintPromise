## 🐍 PYTHON — `sorted()` vs `.sort()`, Stability, Multi-Key Sorts

### Intuition

You already know `sorted(key=lambda ...)` from Day 10. Today fills in the two things that quietly matter once you use it for real: **which flavor of sort mutates your data** (and which doesn't), and **what actually happens to ties** — because "ties" are exactly what a second sort key exists to break.

### The Essentials

```python
# sorted() returns a NEW list — the original is untouched
nums = [5, 2, 8, 1, 9]
new_list = sorted(nums)
nums            # [5, 2, 8, 1, 9] — unchanged

# .sort() sorts IN PLACE and returns None
nums.sort()
nums            # [1, 2, 5, 8, 9] — mutated
# nums = nums.sort()   # BUG: this makes nums None
```

Rule of thumb: `.sort()` when you own the list and are fine mutating it (usually a little faster, no copy). `sorted()` for everything else — a tuple, someone else's list, or a `dict.items()` view — where you either can't mutate in place or don't want to.

### Stability — what happens to ties

```python
students = [("Dee", 85), ("Amy", 90), ("Cal", 85), ("Bob", 90)]
sorted(students, key=lambda s: s[1])
# [('Dee', 85), ('Cal', 85), ('Amy', 90), ('Bob', 90)]
# Dee comes before Cal — both scored 85, and Dee was first in the input.
# Python's sort NEVER reorders equal-key elements relative to each other.
```

That guarantee — **stable sort** — is what makes multi-key sorting possible without a multi-key comparator.

### Multi-key sort with tuples

```python
# Score DESC, name ASC as the tiebreaker — one key function, one pass
ranked = sorted(students, key=lambda s: (-s[1], s[0]))
# [('Amy', 90), ('Bob', 90), ('Cal', 85), ('Dee', 85)]
# Ties broken ALPHABETICALLY: Cal before Dee.
```

Tuples compare element-by-element, so `(-score, name)` sorts primarily by `-score` and only consults `name` when two scores are equal — exactly the "sort by X, then by Y" behavior, in one `key=`.

### The `reverse=True` trap

```python
sorted(students, key=lambda s: s[1], reverse=True)
# [('Amy', 90), ('Bob', 90), ('Dee', 85), ('Cal', 85)]
# Amy before Bob AND Dee before Cal — both just the ORIGINAL input order,
# because reverse=True flips the comparison but stability still refers to
# input order, not to any secondary key. It does NOT re-sort ties alphabetically.
```

`reverse=True` and `key=lambda s: -s[1]` produce the *same primary order* here, but they are not interchangeable the moment a second key is involved — negation only flips the field you negate; `reverse=True` flips the whole comparison and leaves ties exactly where stability puts them (input order, not alphabetical). If you want "score DESC, name ASC," negate the score inside the tuple — don't reach for `reverse=True`.

## 🧩 DSA — Min Stack *(Easy · Stack)*

**NeetCode:** https://neetcode.io/problems/minimum-stack

### The Problem

Design a stack that supports `push`, `pop`, `top`, and `get_min` — all in **O(1)** time. `get_min` has to return the current minimum value in the stack at any point, not just at the top.

### Reading the problem like an engineer

A plain stack already gives you `push`/`pop`/`top` in O(1) — the only new requirement is `get_min()` in O(1) too. The naive move is "just scan the stack and take `min()`," which is correct but O(n) per call. The insight is: the minimum can only ever *change* when you push a new value or pop the value that was the minimum — so if you track the minimum-so-far **at every push**, `get_min()` becomes a lookup of the most recent one, not a search.

### Approach 1 — Brute Force (write this first, always)

```python
class MinStackBrute:
    def __init__(self):
        self.stack = []

    def push(self, val):
        self.stack.append(val)

    def pop(self):
        self.stack.pop()

    def top(self):
        return self.stack[-1]

    def get_min(self):
        return min(self.stack)
        # Time:  O(n) per get_min call — full re-scan
        # Space: O(n) — one stack
```

Correct, and `push`/`pop`/`top` are already O(1) — only `get_min` fails the requirement.

### Approach 2 — Two Stacks (the insight)

```python
class MinStack:
    def __init__(self):
        self.stack = []
        self.min_stack = []

    def push(self, val):
        self.stack.append(val)
        current_min = val if not self.min_stack else min(val, self.min_stack[-1])
        self.min_stack.append(current_min)

    def pop(self):
        self.stack.pop()
        self.min_stack.pop()

    def top(self):
        return self.stack[-1]

    def get_min(self):
        return self.min_stack[-1]

    # Time:  O(1) for every operation
    # Space: O(n) — two stacks, same height
```

### Walkthrough on `push(-2), push(0), push(-3), get_min(), pop(), top(), get_min()`

```
push(-2)  stack=[-2]         min_stack=[-2]            (nothing to compare, -2 is the min)
push(0)   stack=[-2, 0]      min_stack=[-2, -2]         min(0, -2) = -2
push(-3)  stack=[-2, 0, -3]  min_stack=[-2, -2, -3]     min(-3, -2) = -3
get_min() -> min_stack[-1] = -3                          O(1) lookup, no scan
pop()     stack=[-2, 0]      min_stack=[-2, -2]          both stacks pop together
top()     -> stack[-1] = 0
get_min() -> min_stack[-1] = -2                           correctly "forgot" -3 once it was popped
```

### Why a second stack, specifically

Each `min_stack` entry is "the minimum of everything currently below and including this position" — so it grows and shrinks in lockstep with `stack`, and popping `stack` automatically un-computes the minimum back to what it was before the popped value existed. That lockstep property is why it has to be a *stack*, not a single tracked variable: a single `current_min` variable would have no way to "go back up" once the value that set it gets popped.

## ⚡ FASTAPI — Custom Exception Handlers

### Intuition

Every FastAPI app so far has raised `HTTPException` directly inside route bodies and dependencies (Days 6–10). That works, but it means every route has to remember to shape its own error response, and there's no single place to say "every error in this app looks like `{"error": ..., "detail": ...}`." `@app.exception_handler(SomeExceptionType)` inverts that: you raise a plain Python exception anywhere in the app, and one function — registered once — decides how it becomes an HTTP response.

### The Essentials

```python
from fastapi import Request, status
from fastapi.responses import JSONResponse

class StockNotFoundError(Exception):
    def __init__(self, stock_id: int):
        self.stock_id = stock_id

@app.exception_handler(StockNotFoundError)
def stock_not_found_handler(request: Request, exc: StockNotFoundError):
    return JSONResponse(
        status_code=status.HTTP_404_NOT_FOUND,
        content={"error": "stock_not_found", "detail": f"stock {exc.stock_id} not found"},
    )

# Anywhere in the app — a route, a dependency, doesn't matter:
def get_stock_or_404(stock_id: int):
    if stock_id not in stock_db:
        raise StockNotFoundError(stock_id)   # no response-shaping here at all
    return stock_db[stock_id]
```

The dependency's only job is deciding *whether* something went wrong; the handler's only job is deciding *what the client sees*. That split is what stops every route from re-inventing its own error JSON shape.

### Overriding FastAPI's own validation errors

```python
from fastapi.exceptions import RequestValidationError

@app.exception_handler(RequestValidationError)
def validation_handler(request: Request, exc: RequestValidationError):
    return JSONResponse(
        status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
        content={"error": "validation_error", "detail": exc.errors()},
    )
```

`RequestValidationError` is what Pydantic raises automatically on a malformed request body — it already exists whether you handle it or not. Registering a handler for it means even *automatic* validation failures come back in the same `{"error", "detail"}` envelope as your own custom exceptions, instead of FastAPI's default body shape.

## 🔗 COMBINED TASK — Wiring All Three

Every stock now gets its own `MinStack` (today's DSA class, not a `Depends()` this time — a plain object stored per stock) that tracks the running minimum price as new prices are appended via `POST /stocks/{id}/prices`. `GET /stocks/ranked` sorts every stock by `(-avg_price, ticker)` — today's Python multi-key tuple insight — and both `StockNotFoundError` and `EmptyPricesError` are raised as plain exceptions and turned into responses entirely by the handlers registered above, not by the route bodies themselves.

```python
# main.py — Day 11 combined pieces

class MinStack:
    def __init__(self):
        self.stack = []
        self.min_stack = []

    def push(self, val):
        self.stack.append(val)
        current_min = val if not self.min_stack else min(val, self.min_stack[-1])
        self.min_stack.append(current_min)

    def get_min(self):
        return self.min_stack[-1]


min_stacks = {}


@app.get("/stocks/ranked")
def ranked_stocks():
    def avg_price(item):
        return sum(item[1]["prices"]) / len(item[1]["prices"])

    ordered = sorted(stock_db.items(), key=lambda item: (-avg_price(item), item[1]["ticker"]))
    return [{"id": sid, **data, "avg_price": avg_price((sid, data))} for sid, data in ordered]


@app.post("/stocks/{stock_id}/prices")
def add_price(stock_id: int, price: int, stock: dict = Depends(get_stock_or_404)):
    stock_db[stock_id]["prices"].append(price)
    min_stacks[stock_id].push(price)
    return {"id": stock_id, "price_added": price, "running_min": min_stacks[stock_id].get_min()}
```

## 🔑 CONCEPT ANSWER

**Question:** "Why does Python's sort guarantee stability, and why does that specifically make `key=lambda s: (-score, name)` work for a multi-key sort where `reverse=True` wouldn't?"

**Answer:** Python's sort (Timsort) is defined to never swap two elements that compare equal under the key function — their relative order from the input is always preserved. That guarantee is what lets a single key function express a multi-key sort at all: `(-score, name)` sorts primarily by `-score`, and *only* falls back to comparing `name` when two `-score` values tie, because tuple comparison itself checks the first element first and only looks at the second when the first is equal — stability isn't even needed there, since the key values themselves differ whenever score differs. `reverse=True`, by contrast, doesn't add a second key at all — it just flips the *direction* of comparison on the one key you gave it, and stability still refers to original input order for anything that ties on that one key. So `reverse=True` can approximate "sort DESC" for a single field, but it has no way to say "and break ties by name ASC" — there's no second key in the picture for it to consult.
