## 🐍 PYTHON — `@property`, Validated Setters & Computed Attributes

### Intuition

`self.prices = prices` inside `__init__` (Days 16–17) accepts anything — a list, a string, `None`, nothing stops it. A **property** turns an attribute into a pair of methods (a getter and a setter) that still get *used* like a plain attribute (`acme.prices`, `acme.prices = [...]`) but run validation or computation every time.

### The Essentials

```python
class Stock:
    def __init__(self, ticker: str, prices: list[int]):
        self.ticker = ticker
        self.prices = prices          # goes through the setter below, even in __init__

    @property
    def prices(self) -> list[int]:
        return self._prices

    @prices.setter
    def prices(self, value: list[int]):
        if not all(isinstance(p, (int, float)) and p >= 0 for p in value):
            raise ValueError("all prices must be non-negative numbers")
        self._prices = value

    @property
    def latest_price(self) -> int:
        return self._prices[-1] if self._prices else 0


acme = Stock("ACME", [10, 20, 30])
print(acme.prices)          # [10, 20, 30] — reads like a plain attribute
print(acme.latest_price)    # 30 — computed on every access, never stored

acme.prices = [15, 25]      # goes through the setter, validated
print(acme.latest_price)    # 25 — recomputed automatically

acme.prices = [-5]          # ValueError: all prices must be non-negative numbers
```

### Why `self._prices` and not `self.prices` inside the property

If the getter or setter referred to `self.prices` instead of `self._prices`, calling `acme.prices` would call the getter, which would call `self.prices` again, which would call the getter again — infinite recursion. `_prices` (single leading underscore — Python's convention for "internal, not part of the public interface") is the actual storage; `prices` is the public-facing name that happens to be backed by a property instead of a plain attribute.

### `latest_price` — a property with no setter at all

`latest_price` only defines `@property`, no `@latest_price.setter` — which makes `acme.latest_price = 100` raise `AttributeError: can't set attribute`. It's **read-only by construction**: there's no sensible way to "set" the latest price independent of the price list itself, so the property simply doesn't offer a way to.

### Why this matters more than it looks like it does

```python
# Without @property (Days 16-17):
acme.prices = "oops, a typo"   # silently accepted, breaks total_value() later, far from here

# With @property (today):
acme.prices = "oops, a typo"   # raises ValueError immediately, at the point of the mistake
```

The whole value of a validated setter is *where* the error surfaces — at the exact line that caused it, instead of three function calls later inside `total_value()` when `sum("oops, a typo")` throws a confusing `TypeError` that gives no hint the real problem was an assignment far upstream.

## 🧩 DSA — Merge Two Sorted Lists *(Easy · Linked List)*

**NeetCode:** https://neetcode.io/problems/merge-two-sorted-linked-lists

### The Problem

Given the heads of two sorted linked lists, merge them into one sorted linked list and return its head.

### Reading the problem like an engineer

Day 16 read a linked list, Day 17 rewrote one in place — this is the first problem that combines *two* of them. Both inputs are already sorted, which is the same gift Day 14's Binary Search input gave you: because each list is individually sorted, comparing just the two front nodes is always enough to know which one belongs next in the output.

### Approach 1 — Brute Force: collect both, sort, rebuild

```python
def merge_two_lists_brute(l1, l2):
    values = []
    for node in (l1, l2):
        while node:
            values.append(node.val)
            node = node.next
    values.sort()
    dummy = ListNode()
    curr = dummy
    for v in values:
        curr.next = ListNode(v)
        curr = curr.next
    return dummy.next
    # Time:  O((n+m) log(n+m)) — sorting throws away the fact both inputs were already sorted
    # Space: O(n+m)
```

### Approach 2 — Two-Pointer Merge with a Dummy Head (the insight)

```python
def merge_two_lists(l1, l2):
    dummy = ListNode()
    curr = dummy
    while l1 and l2:
        if l1.val <= l2.val:
            curr.next = l1
            l1 = l1.next
        else:
            curr.next = l2
            l2 = l2.next
        curr = curr.next
    curr.next = l1 if l1 else l2    # attach whichever list still has leftovers
    return dummy.next
    # Time:  O(n+m) — each node visited exactly once
    # Space: O(1) — reuses existing nodes, no new ones created
```

### Walkthrough on `l1 = [1, 2, 4]`, `l2 = [1, 3, 4]`

```
dummy -> ?                    l1=1, l2=1
1<=1 -> curr.next=l1(1), l1=2, curr=1        dummy -> 1
l1=2, l2=1: 2<=1? no -> curr.next=l2(1), l2=3, curr=1   dummy -> 1 -> 1
l1=2, l2=3: 2<=3 -> curr.next=l1(2), l1=4, curr=2       dummy -> 1 -> 1 -> 2
l1=4, l2=3: 4<=3? no -> curr.next=l2(3), l2=4, curr=3   dummy -> 1 -> 1 -> 2 -> 3
l1=4, l2=4: 4<=4 -> curr.next=l1(4), l1=None, curr=4    dummy -> 1 -> 1 -> 2 -> 3 -> 4
l1 is None -> loop ends -> curr.next = l2 (still has [4])

Result: 1 -> 1 -> 2 -> 3 -> 4 -> 4
```

### Why the dummy head, specifically

Without it, the very first node of the merged list would need special-case code (`if not result: result = ...`) to decide which of `l1[0]` or `l2[0]` becomes the head before the loop even starts. `dummy` is a throwaway node that exists purely so `curr.next = ...` always has something valid to attach to from the first iteration — `dummy.next` (not `dummy` itself) is the real answer, since `dummy` was never a real node of the merged list to begin with.

## ⚡ FASTAPI — Lifespan-Managed Resource Pooling

### Intuition

Day 12's lifespan hook held one value — a request counter — set at startup and read at shutdown. Real apps often need something richer at startup: a **pool** of reusable resources (database connections, in this case simulated) that requests borrow from and return, instead of creating fresh every time.

### The Essentials

```python
from contextlib import asynccontextmanager

class ConnectionPool:
    def __init__(self, size: int):
        self._available = [f"conn-{i}" for i in range(size)]

    def acquire(self) -> str:
        if not self._available:
            raise RuntimeError("pool exhausted")
        return self._available.pop()

    def release(self, conn: str) -> None:
        self._available.append(conn)


app_state = {}


@asynccontextmanager
async def lifespan(app: FastAPI):
    app_state["pool"] = ConnectionPool(size=3)     # built once at startup
    yield
    app_state["pool"] = None                        # torn down once at shutdown


def get_pool() -> ConnectionPool:
    return app_state["pool"]
```

`ConnectionPool` is today's Python lesson in miniature — `_available` is internal state prefixed with `_`, and `acquire`/`release` are the controlled interface around it, the same shape as `Stock`'s `_prices` behind `@property`.

### Why a pool instead of one connection

A single shared connection means every request queues behind whichever one is currently using it. A pool sized to expected concurrency lets several requests borrow different connections at once, and `acquire()` — by raising when `_available` is empty rather than silently returning `None` — makes "the pool is out of capacity" an explicit, catchable error instead of a request that mysteriously gets a broken connection.

### Wiring it through `Depends()`

```python
from fastapi import Depends

@app.get("/db-check")
def db_check(pool: ConnectionPool = Depends(get_pool)) -> dict:
    conn = pool.acquire()
    try:
        return {"used_connection": conn}
    finally:
        pool.release(conn)
```

This is Day 9's dependency injection pattern, unchanged — `get_pool` just now returns something built once at startup by `lifespan`, instead of something computed fresh per request.

## 🔗 COMBINED TASK — Wiring All Three

Two separate linked lists — one built from the stocks created so far, one representing a second sorted batch — get combined with today's `merge_two_lists()` into a single sorted-by-ticker chain. Each `StockNode`'s `prices` now goes through today's validated `@property` setter, so a malformed batch fails immediately at construction instead of corrupting the merge. Because `merge_two_lists` rewires `next` pointers **in place** rather than copying nodes, the two input chains are rebuilt fresh on every request — reusing the same nodes across two merges would let the second call rewire pointers the first call already rewired, silently producing exactly the kind of corrupted, self-referencing chain Day 16's `has_cycle()` exists to catch. The merge operation itself is recorded through a lifespan-managed `ConnectionPool`-style "audit log," acquired via `Depends()` exactly like Day 9, proving the pool hands out and reclaims connections correctly across two consecutive requests.

```python
# main.py — Day 18 combined pieces

class StockNode:
    def __init__(self, ticker: str, prices: list[int], next: "StockNode | None" = None):
        self.ticker = ticker
        self.prices = prices          # validated by the setter below
        self.next = next

    @property
    def prices(self) -> list[int]:
        return self._prices

    @prices.setter
    def prices(self, value: list[int]):
        if not all(isinstance(p, (int, float)) and p >= 0 for p in value):
            raise ValueError("all prices must be non-negative numbers")
        self._prices = value


def merge_two_lists(l1, l2, key=lambda node: node.ticker):
    dummy = StockNode("", [])
    curr = dummy
    while l1 and l2:
        if key(l1) <= key(l2):
            curr.next, l1 = l1, l1.next
        else:
            curr.next, l2 = l2, l2.next
        curr = curr.next
    curr.next = l1 if l1 else l2
    return dummy.next


@app.post("/stocks/merge")
def merge_stocks(pool: ConnectionPool = Depends(get_pool)) -> dict:
    conn = pool.acquire()
    try:
        # Fresh chains each call — merge_two_lists rewires nodes in place,
        # so reusing the same nodes across requests would corrupt them.
        batch_a = build_chain([("ACME", [10]), ("MID", [7]), ("ZED", [5])])
        batch_b = build_chain([("BETA", [3]), ("NOVA", [9])])
        merged = merge_two_lists(batch_a, batch_b)
        order, node = [], merged
        while node:
            order.append(node.ticker)
            node = node.next
        return {"merged_order": order, "audit_connection": conn}
    finally:
        pool.release(conn)
```

## 🔑 CONCEPT ANSWER

**Question:** "`latest_price` recomputes `self._prices[-1]` on every single access instead of storing it as a plain attribute set once in `__init__`. Why is that the right tradeoff here?"

**Answer:** If `latest_price` were stored as a plain attribute set once in `__init__`, it would go stale the moment `prices` changed afterward — `acme.prices = [15, 25]` would leave `acme.latest_price` still reporting the old value from construction, unless every single place in the codebase that ever mutates `prices` also remembered to update `latest_price` in lockstep, which is exactly the kind of bookkeeping that gets forgotten in one code path and causes a hard-to-find bug. Computing it fresh from `self._prices[-1]` on every access costs one list-index lookup — essentially free — and makes it *structurally impossible* for `latest_price` to disagree with `prices`, because there's no separate stored value that could ever drift out of sync. The tradeoff only stops being obviously right when the computation itself is expensive (say, re-summing a million-element list on every access) — for a single index lookup, recomputing is strictly safer than caching, and `@property` is what makes that "always recompute" behavior invisible to every caller, who still just writes `acme.latest_price` either way.
