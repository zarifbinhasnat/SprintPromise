## 🐍 PYTHON — Instance, Class & Static Methods, `__repr__`

### Intuition

`Stock.total_value(self)` from Day 16 is an **instance method** — it needs a specific stock to operate on. Not everything a class does needs that. A **classmethod** receives the *class itself* (`cls`) instead of an instance, which makes it the standard way to write an alternate constructor. A **staticmethod** receives neither — it's a plain function that happens to live inside the class namespace because it's conceptually related.

### The Essentials

```python
class Stock:
    def __init__(self, ticker: str, prices: list[int]):
        self.ticker = ticker
        self.prices = prices

    def total_value(self) -> int:          # instance method — needs self
        return sum(self.prices)

    @classmethod
    def from_dict(cls, data: dict) -> "Stock":   # classmethod — needs cls, not self
        return cls(data["ticker"], data["prices"])

    @staticmethod
    def is_valid_ticker(ticker: str) -> bool:    # staticmethod — needs neither
        return ticker.isupper() and ticker.isalpha()

    def __repr__(self) -> str:
        return f"Stock(ticker={self.ticker!r}, total_value={self.total_value()})"


acme = Stock.from_dict({"ticker": "ACME", "prices": [10, 20, 30]})
print(acme)                              # Stock(ticker='ACME', total_value=60)
print(Stock.is_valid_ticker("ACME"))     # True
print(Stock.is_valid_ticker("acme123"))  # False
```

### Why `from_dict` is a classmethod, not a plain function

`cls` inside `from_dict` refers to `Stock` itself — not any particular stock, because none exists yet; the whole point of the method is to build one. `cls(data["ticker"], data["prices"])` calls `Stock(...)` exactly the way `Stock(...)` would if written by hand, except it goes through the class reference instead of hardcoding the class name. That matters the moment a subclass exists: `cls` adapts, a hardcoded `Stock(...)` inside the method body wouldn't.

### Why `is_valid_ticker` is a staticmethod, not an instance method

Validating a ticker string doesn't need `self.ticker` or `self.prices` — it needs only the string handed in as an argument. Making it a method of `Stock` anyway groups it with the class it conceptually belongs to (you'd look for ticker validation *on* `Stock`, not as some loose module-level function), but it takes no automatic first parameter, because there's no instance state to reach for.

### `__repr__` — what `print()` shows without it

```python
class StockNoRepr:
    def __init__(self, ticker):
        self.ticker = ticker

print(StockNoRepr("ACME"))
# <__main__.StockNoRepr object at 0x7f2a1c0d5490> — useless for debugging
```

`__repr__` is a **dunder method** (double-underscore, "double under") — a hook Python calls automatically in specific situations, here whenever something tries to turn the object into a string for display. Defining it once means every `print(acme)`, every entry in a list you print, and every value shown in a debugger all read as `Stock(ticker='ACME', total_value=60)` instead of a meaningless memory address.

## 🧩 DSA — Reverse Linked List *(Easy · Linked List)*

**NeetCode:** https://neetcode.io/problems/reverse-a-linked-list

### The Problem

Given the head of a singly linked list, reverse it in place and return the new head.

### Reading the problem like an engineer

Yesterday's cycle detection only ever *read* `next` pointers. This is the first linked-list problem that *rewrites* them — every node's `next` has to end up pointing at the node that used to come before it, and the trap is that once you overwrite `node.next`, you've lost the only way to reach the rest of the original list, unless you saved a reference to it first.

### Approach 1 — Brute Force: collect values, rebuild

```python
def reverse_list_brute(head):
    values = []
    node = head
    while node:
        values.append(node.val)
        node = node.next
    dummy = ListNode()
    curr = dummy
    for v in reversed(values):
        curr.next = ListNode(v)
        curr = curr.next
    return dummy.next
    # Time:  O(n)
    # Space: O(n) — a new list of values, plus n new nodes
```

Correct, but it builds an entirely new chain of nodes instead of reusing the ones already there — throwing away structure the input already gave you for free.

### Approach 2 — Iterative, in place (the insight)

```python
def reverse_list(head):
    prev, curr = None, head
    while curr:
        next_node = curr.next   # save it BEFORE overwriting curr.next
        curr.next = prev        # reverse the pointer
        prev = curr              # advance prev
        curr = next_node         # advance curr using the saved reference
    return prev                  # prev ends up at the old tail — the new head
    # Time:  O(n)
    # Space: O(1) — three pointers, no new nodes
```

### Walkthrough on `1 -> 2 -> 3 -> None`

```
prev=None, curr=1
  next_node=2, curr(1).next=None (=prev), prev=1, curr=2
prev=1, curr=2
  next_node=3, curr(2).next=1 (=prev), prev=2, curr=3
prev=2, curr=3
  next_node=None, curr(3).next=2 (=prev), prev=3, curr=None
loop ends (curr is None) -> return prev = 3

Result: 3 -> 2 -> 1 -> None
```

The line that makes this work is `next_node = curr.next` coming *first*, on its own, before `curr.next` gets overwritten — that single saved reference is the only thing standing between "reversed list" and "list that's lost everything after node 1."

### Why the iterative approach, specifically

This is the first problem in the track where the entire solution is three pointers marching forward together while rewriting one pointer per step. There's also a recursive version (reverse everything after the head, then splice the head onto the end) that's worth knowing conceptually, but it costs O(n) call-stack space where the iterative version costs O(1) — the same brute-force-vs-optimal space tradeoff that's shown up since Day 1's Two Sum.

## ⚡ FASTAPI — Middleware Ordering & `GZipMiddleware`

### Intuition

Yesterday added one class-based middleware. Real apps stack several — logging, compression, CORS, auth. `app.add_middleware()` can be called more than once, and **the order you call it in changes what actually happens to a request**, because middleware wraps around the app like layers of an onion.

### The Essentials

```python
from fastapi.middleware.gzip import GZipMiddleware

app = FastAPI()
app.add_middleware(TimingLoggerMiddleware, logger=logger)   # registered first
app.add_middleware(GZipMiddleware, minimum_size=500)         # registered second
```

### The onion model — why registration order runs backwards on the way in

Starlette wraps each middleware around the *previous* stack, so the **last one registered ends up as the outermost layer**. A request travels inward through layers in reverse-registration order, hits the route, then travels back outward through the same layers to build the response:

```
request  -> GZipMiddleware (outer, registered last)
         -> TimingLoggerMiddleware (inner, registered first)
         -> route handler
response <- TimingLoggerMiddleware   (logs the size BEFORE compression)
         <- GZipMiddleware            (compresses last, right before it leaves the app)
```

### Why this specific order matters

If `TimingLoggerMiddleware` were registered *after* `GZipMiddleware` instead, it would sit outside the compression layer and log the *compressed* byte size and a timing measurement that includes gzip's own compression work — muddying exactly what Day 14's logging middleware was built to measure: how long the route itself took. Registering the logger first (making it the inner layer) means it wraps only the route handler's own work, and compression happens as a separate, later step it never has to account for.

## 🔗 COMBINED TASK — Wiring All Three

`StockNode` gains a `@classmethod from_pydantic()` — an alternate constructor built from today's Python lesson, converting a validated `StockIn` request body straight into a linked-list node — and a `__repr__` so the reversed list is readable when logged. `POST /stocks/reverse` walks the existing linked list built across Day 16 and today, applies `reverse_list()` from today's DSA section, and swaps in the new head — all wrapped by both `TimingLoggerMiddleware` (inner) and `GZipMiddleware` (outer), registered in that order for the reason explained above.

```python
# main.py — Day 17 combined pieces

class StockNode:
    def __init__(self, ticker: str, prices: list[int], next: "StockNode | None" = None):
        self.ticker = ticker
        self.prices = prices
        self.next = next

    @classmethod
    def from_pydantic(cls, payload) -> "StockNode":
        return cls(payload.ticker, payload.prices)

    def __repr__(self) -> str:
        return f"StockNode({self.ticker!r})"


def reverse_list(head):
    prev, curr = None, head
    while curr:
        next_node = curr.next
        curr.next = prev
        prev = curr
        curr = next_node
    return prev


@app.post("/stocks/reverse")
def reverse_stocks() -> dict:
    global _head
    _head = reverse_list(_head)
    result, node = [], _head
    while node:
        result.append(repr(node))
        node = node.next
    return {"order": result}
```

    return prev


def to_list(head):

        head = head.next

# fastapi/17_middleware_ordering_gzip/main.py
# Run: uvicorn main:app --reload

import logging
import time
from fastapi import FastAPI
from fastapi.middleware.gzip import GZipMiddleware
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
from pydantic import BaseModel

logging.basicConfig(level=logging.INFO, format="%(asctime)s %(message)s")
logger = logging.getLogger("sprint")


class StockNode:
    def __init__(self, ticker: str, prices: list, next=None):
        self.ticker = ticker
        self.prices = prices
        self.next = next

    @classmethod
    def from_pydantic(cls, payload) -> "StockNode":
        return cls(payload.ticker, payload.prices)

    def __repr__(self) -> str:
        return f"StockNode({self.ticker!r})"


def reverse_list(head):
    prev, curr = None, head
    while curr:
        next_node = curr.next
        curr.next = prev
        prev = curr
        curr = next_node
    return prev


class TimingLoggerMiddleware(BaseHTTPMiddleware):
    def __init__(self, app, logger):
        super().__init__(app)
        self.logger = logger

    async def dispatch(self, request: Request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        duration_ms = (time.perf_counter() - start) * 1000
        self.logger.info(f"{request.method} {request.url.path} -> {response.status_code} ({duration_ms:.2f}ms)")
        return response


app = FastAPI(title="Sprint Day 17")
app.add_middleware(TimingLoggerMiddleware, logger=logger)  # inner: registered first
app.add_middleware(GZipMiddleware, minimum_size=1)           # outer: registered second

_head = None
_tail = None


class StockIn(BaseModel):
    ticker: str
    prices: list[int]


@app.get("/")
def root() -> dict:
    return {"message": "Sprint Day 17 is running.", "day": 17}


@app.post("/stocks", status_code=201)
def create_stock(payload: StockIn) -> dict:
    global _head, _tail
    node = StockNode.from_pydantic(payload)
    if _head is None:
        _head = _tail = node
    else:
        _tail.next = node
        _tail = node
    return {"ticker": payload.ticker, "prices": payload.prices}


@app.post("/stocks/reverse")
def reverse_stocks() -> dict:
    global _head
    _head = reverse_list(_head)
    result, node = [], _head
    while node:
        result.append(repr(node))
        node = node.next
    return {"order": result}

## 🔑 CONCEPT ANSWER

**Question:** "Why does `Stock.from_dict` use `cls(...)` inside it instead of just writing `Stock(...)` directly, given that `cls` and `Stock` refer to the same class in this example?"

**Answer:** In this exact example they produce the same result, because `from_dict` is only ever called as `Stock.from_dict(...)`, so `cls` is bound to `Stock`. The reason to prefer `cls(...)` shows up the moment a subclass enters the picture: if `class PennyStock(Stock): pass` is defined and someone calls `PennyStock.from_dict({...})`, `cls` inside the classmethod is automatically bound to `PennyStock`, not `Stock` — so `cls(...)` correctly constructs a `PennyStock` instance. A hardcoded `Stock(...)` inside the method body would ignore that entirely and always build a plain `Stock`, even when called through a subclass — silently handing back the wrong type. `@classmethod` exists specifically so alternate constructors keep working correctly under inheritance without needing to know in advance every subclass that might ever call them.
