## 🐍 PYTHON — Classes & `__init__`

### Intuition

Every stock in this track since Day 3 has been a `dict`: `{"ticker": "ACME", "prices": [10, 20]}`. That works, but nothing stops a typo — `{"tikcer": "ACME"}` is a dict Python will accept without complaint, and there's no single place that says "a stock has exactly these fields, and here's what you can do with one." A **class** is that place: a blueprint for a kind of object, bundling its data (attributes) and its behavior (methods) together.

### The Essentials

```python
class Stock:
    def __init__(self, ticker: str, prices: list[int]):
        self.ticker = ticker
        self.prices = prices

    def total_value(self) -> int:
        return sum(self.prices)


acme = Stock("ACME", [10, 20, 30])
print(acme.ticker)          # "ACME"
print(acme.total_value())   # 60
```

`__init__` runs automatically the moment `Stock("ACME", [10, 20, 30])` is called — it's the constructor. `self` is the instance being built; `self.ticker = ticker` is what turns a plain argument into something that sticks around on the object for as long as it exists. Every method defined inside the class automatically receives that same instance as its first parameter, named `self` by convention.

### Why `self` isn't optional

```python
class Stock:
    def total_value(self):
        return sum(self.prices)     # without self, there's no way to reach THIS stock's prices
```

`acme.total_value()` is really `Stock.total_value(acme)` under the hood — Python passes the instance in automatically when you call it through dot notation. Drop `self` from the parameter list and `total_value()` has no way to know which stock's prices to sum.

### Multiple instances, independent state

```python
acme = Stock("ACME", [10, 20, 30])
zed = Stock("ZED", [5, 5])

acme.prices.append(40)
print(acme.total_value())   # 100
print(zed.total_value())    # 10 — completely unaffected
```

This is the thing a dict never gave you for free: two `Stock` objects are two separate boxes of state. Mutating one's `prices` list has zero effect on the other, because `self.prices` on each instance points at its own list, created fresh inside its own call to `__init__`.

### Classes vs. the dicts used through Day 15

```python
# The old way (Days 3-15):
stock = {"ticker": "ACME", "prices": [10, 20]}
total = sum(stock["prices"])

# Today's way:
stock = Stock("ACME", [10, 20])
total = stock.total_value()
```

Both work. The difference is where the logic lives: with the dict, "how do I total a stock's prices" is a question every caller has to answer themselves, correctly, every time. With the class, `total_value()` lives with the data it operates on — write it once, correctly, and every caller just asks the object.

## 🧩 DSA — Linked List Cycle *(Easy · Linked List)*

**NeetCode:** https://neetcode.io/problems/linked-list-cycle-detection

### The Problem

Given the head of a singly linked list, determine whether it contains a cycle — some node's `next` pointer loops back to a node earlier in the list instead of eventually reaching `None`.

### Reading the problem like an engineer

This is the first problem in the track built on a `next`-pointer structure instead of an array — which is exactly why today's Python lesson matters: a linked list node is a small class, `self.val` and `self.next`, no different in spirit from `self.ticker` and `self.prices` on `Stock`. The challenge itself is that you can't just "look at the whole list" the way you slice an array — if there's a cycle, walking it naively never terminates.

```python
class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next
```

### Approach 1 — Brute Force: a seen-set

```python
def has_cycle_brute(head: ListNode) -> bool:
    seen = set()
    node = head
    while node:
        if node in seen:
            return True
        seen.add(node)
        node = node.next
    return False
    # Time:  O(n) — visits each node once
    # Space: O(n) — the seen set can hold every node
```

Correct, and it terminates even with a cycle, because the *second* visit to a repeated node is caught by the set before recursing forever. But it pays for that safety with O(n) extra memory.

### Approach 2 — Floyd's Tortoise and Hare (the insight)

```python
def has_cycle(head: ListNode) -> bool:
    slow, fast = head, head
    while fast and fast.next:
        slow = slow.next          # moves 1 step
        fast = fast.next.next     # moves 2 steps
        if slow is fast:
            return True            # they met -> cycle
    return False
    # Time:  O(n)
    # Space: O(1) — just two pointers, no extra structure
```

### Walkthrough on a 4-node list with a cycle: `3 -> 2 -> 0 -> -4 -> (back to 2)`

```
slow=3, fast=3
step 1: slow=2,  fast=0
step 2: slow=0,  fast=2     (fast wrapped through -4 back to 2, then to 0)
step 3: slow=-4, fast=0
step 4: slow=2,  fast=2     -> slow is fast -> CYCLE DETECTED
```

If there were no cycle, `fast` would hit `None` first (since it moves twice as fast) and the loop would exit cleanly returning `False` — there's no scenario where a cycle-free list makes `fast` chase `slow` forever, because `fast` runs out of list before that could happen.

### Why the tortoise and hare, specifically

Every algorithm through Day 14 either scanned once or used a dict for O(1) lookups purchased with O(n) space. This is the first problem where the trick is **two pointers moving at different speeds through the same structure** — if a cycle exists, the faster pointer is guaranteed to lap the slower one and land on the exact same node, the same way a runner on a circular track eventually laps a slower runner without either of them needing to remember where they've already been.

## ⚡ FASTAPI — Class-Based Middleware (`BaseHTTPMiddleware`)

### Intuition

Days 8, 12, and 14 all wrote middleware the same way: a plain `async def` function decorated with `@app.middleware("http")`. That works for one function per app. Starlette (which FastAPI sits on top of) also lets you write middleware as a **class** — and today's Python lesson is exactly what makes that readable: a middleware class is just a class with `__init__` and a method, the same shape as `Stock`.

### The Essentials

```python
from starlette.middleware.base import BaseHTTPMiddleware
from starlette.requests import Request
import time


class TimingLoggerMiddleware(BaseHTTPMiddleware):
    def __init__(self, app, logger):
        super().__init__(app)
        self.logger = logger              # exactly today's Python lesson: self stores state

    async def dispatch(self, request: Request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        duration_ms = (time.perf_counter() - start) * 1000
        self.logger.info(f"{request.method} {request.url.path} -> {response.status_code} ({duration_ms:.2f}ms)")
        return response


app.add_middleware(TimingLoggerMiddleware, logger=logger)
```

`dispatch()` plays the exact role Day 14's `log_requests(request, call_next)` function played — everything before `call_next` runs pre-route, everything after runs post-route. The difference is `self`: because this is a class, `__init__` can accept and store configuration (here, a logger instance) once, at registration time, instead of relying on module-level globals.

### Why reach for a class instead of the decorator function

A function-based middleware has no natural place to hold configuration — Day 14's version used a module-level `logger`, which works for one app but doesn't compose if you want two different loggers for two mounted sub-apps. A class-based middleware takes its configuration through `__init__`, exactly like `Stock("ACME", [10, 20])` takes its ticker and prices — `app.add_middleware(TimingLoggerMiddleware, logger=logger)` passes `logger` straight into the constructor, same mechanism, new context.

## 🔗 COMBINED TASK — Wiring All Three

A `StockNode` class (today's Python lesson, shaped like `ListNode`) holds a ticker, its prices, and a `next` pointer, so the API's in-memory storage becomes an actual singly linked list instead of Day 14's sorted array. Before `GET /stocks` serializes that list, it runs today's `has_cycle()` as an integrity check — if a bug ever corrupted the list's `next` pointers into a loop, the check catches it and raises, instead of the endpoint hanging forever walking a list that never ends. `TimingLoggerMiddleware`, today's class-based middleware, wraps every request the same way Day 14's function did, just built from `self` and `__init__` instead of a bare function.

```python
# main.py — Day 16 combined pieces

class StockNode:
    def __init__(self, ticker: str, prices: list[int], next: "StockNode | None" = None):
        self.ticker = ticker
        self.prices = prices
        self.next = next

    def total_value(self) -> int:
        return sum(self.prices)


def has_cycle(head: StockNode | None) -> bool:
    slow, fast = head, head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            return True
    return False


head: StockNode | None = None
tail: StockNode | None = None


def append_stock(ticker: str, prices: list[int]) -> None:
    global head, tail
    node = StockNode(ticker, prices)
    if head is None:
        head = tail = node
    else:
        tail.next = node
        tail = node


@app.get("/stocks")
def list_stocks() -> dict:
    if has_cycle(head):
        raise RuntimeError("corrupted stock list: cycle detected")   # never hit in normal operation
    result, node = [], head
    while node:
        result.append({"ticker": node.ticker, "total_value": node.total_value()})
        node = node.next
    return {"stocks": result}
```

```python
# dsa/linked_list/01_linked_list_cycle.py

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next


def has_cycle_brute(head):
    seen = set()
    node = head
    while node:
        if node in seen:
            return True
        seen.add(node)
        node = node.next
    return False


def has_cycle(head):
    slow, fast = head, head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
        if slow is fast:
            return True
    return False


def build_cyclic_list(values, pos):
    nodes = [ListNode(v) for v in values]
    for i in range(len(nodes) - 1):
        nodes[i].next = nodes[i + 1]
    if pos != -1:
        nodes[-1].next = nodes[pos]
    return nodes[0] if nodes else None


if __name__ == "__main__":
    cases = [
        ([3, 2, 0, -4], 1, True),
        ([1, 2], 0, True),
        ([1], -1, False),
        ([1, 2, 3, 4, 5], -1, False),
    ]
    for values, pos, expected in cases:
        head = build_cyclic_list(values, pos)
        result = has_cycle(head)
        status = "PASS" if result == expected else "FAIL"
        print(f"[{status}]  has_cycle({values}, pos={pos}) -> {result}")
```

```python
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
```

```python
class TimingLoggerMiddleware(BaseHTTPMiddleware):
    def __init__(self, app, logger):
        super().__init__(app)
        self.logger = logger

    async def dispatch(self, request: Request, call_next):

        duration_ms = (time.perf_counter() - start) * 1000
        self.logger.info(f"{request.method} {request.url.path} -> {response.status_code} ({duration_ms:.2f}ms)")

app.add_middleware(TimingLoggerMiddleware, logger=logger)

_head = None
_tail = None


class StockIn(BaseModel):
    ticker: str
    prices: list[int]


@app.get("/")
def root() -> dict:
    return {"message": "Sprint Day 16 is running.", "day": 16}


@app.post("/stocks", status_code=201)
def create_stock(payload: StockIn) -> dict:
    global _head, _tail
    node = StockNode(payload.ticker, payload.prices)
    if _head is None:
        _head = _tail = node
    else:
        _tail.next = node
        _tail = node
    return {"ticker": payload.ticker, "prices": payload.prices}

def list_stocks() -> dict:

    result, node = [], _head
    while node:
        result.append({"ticker": node.ticker, "total_value": node.total_value()})
```

## 🔑 CONCEPT ANSWER

**Question:** "Two `Stock` instances are created from the same class. Why does mutating `acme.prices` never affect `zed.prices`, even though both were built by the exact same `__init__`?"

**Answer:** `__init__` runs once *per instance* — every call to `Stock("ACME", [10, 20, 30])` executes `self.prices = prices` against a brand-new, freshly created object, so `acme.prices` and `zed.prices` are two entirely separate list objects in memory from the moment each instance is constructed, even though the same line of code created both of them. `self` inside `__init__` never refers to "the class" — it refers to *this specific instance currently being built*, which is exactly why `acme.prices.append(40)` only ever touches the list that `acme.self` (i.e., the `acme` object) points to. If `prices` had instead been defined as a class-level default — `class Stock: prices = []` outside `__init__` — *that* would be shared across every instance, because it would belong to the class itself rather than to any one object. Defining it inside `__init__` via `self.prices = prices` is precisely what gives every instance its own independent box of state.
