## 🐍 PYTHON — Dicts & Sets Deep Dive

### Intuition

You've used `dict()` since Day 1 for frequency counting, but three things make dicts and sets genuinely powerful instead of just "a container with lookup": comprehensions (build one in a single expression), `.get()` (read safely without a `KeyError`), and set algebra (union/intersection/difference as one operator instead of a loop).

### The Essentials

```python
nums = [1, 2, 3, 4, 5]

# Dict comprehension — same shape as a list comprehension, but key: value
squares = {n: n * n for n in nums}                 # {1:1, 2:4, 3:9, 4:16, 5:25}
evens_only = {n: n * n for n in nums if n % 2 == 0} # filter clause works the same way

# .get(key, default) — never raises, unlike counts[key]
counts = {"a": 3}
counts.get("z")        # None
counts.get("z", 0)     # 0 — this is what makes the increment pattern one line:
counts["z"] = counts.get("z", 0) + 1

# Set comprehension + set algebra
a, b = {1, 2, 3, 4}, {3, 4, 5, 6}
a | b   # union:        {1,2,3,4,5,6}
a & b   # intersection: {3,4}
a - b   # difference:   {1,2}      — in a, not in b
a ^ b   # symmetric diff: {1,2,5,6} — in exactly one of the two
```

### Nested structures

```python
students = {
    "amina": {"grades": [88, 92, 79], "active": True},
    "yusuf": {"grades": [65, 70], "active": False},
}
# a dict of dicts — access chains: students["amina"]["grades"]

records = [{"id": 1, "price": 7}, {"id": 2, "price": 1}]
prices_by_id = {r["id"]: r["price"] for r in records}
# a list of dicts turned into a dict, keyed by id — this exact shape
# is what today's FastAPI in-memory "database" looks like.
```

### Why it matters going forward

`prices_by_id = {r["id"]: r["price"] for r in records}` isn't just a syntax trick — it's the same "index by key for O(1) lookup" idea that made yesterday's seen-set fast, applied to building a dict instead of checking one. You'll use exactly this pattern today to build the in-memory store behind your PUT/DELETE endpoints.

## 🧩 DSA — Best Time to Buy and Sell Stock *(Easy · Arrays)*

**NeetCode:** https://neetcode.io/problems/best-time-to-buy-and-sell-stock

### The Problem

Given an array `prices` where `prices[i]` is the stock price on day `i`, choose one day to buy and a later day to sell to maximize profit. Return the max profit, or `0` if no profit is possible.

### Reading the problem like an engineer

Strip the wrapper: *"As I walk through the prices, what's the best profit if today were the sell day?"* That depends only on the **lowest price seen so far** — you never need to know which earlier day had that low, just its value. This is Day 3's seen-set walk with a twist: instead of tracking "have I seen this value," you're tracking "what's the best value I've seen," and updating a running answer as you go.

### Approach 1 — Brute Force (write this first, always)

```python
def max_profit_brute(prices):
    best = 0
    for i in range(len(prices)):
        for j in range(i + 1, len(prices)):
            profit = prices[j] - prices[i]
            if profit > best:
                best = profit
    return best
    # Time:  O(n²) — every buy/sell pair checked
    # Space: O(1)
```

### Approach 2 — One-Pass Greedy (the insight)

```python
def max_profit(prices):
    if not prices:
        return 0

    min_price = prices[0]
    best_profit = 0
    for price in prices[1:]:
        if price < min_price:
            min_price = price
        else:
            best_profit = max(best_profit, price - min_price)
    return best_profit

    # Time:  O(n) — one pass
    # Space: O(1) — two running variables, no extra structure
```

### Walkthrough on `prices = [7, 1, 5, 3, 6, 4]`

```
min_price=7, best=0
price=1 -> 1 < 7  -> min_price=1
price=5 -> 5-1=4 > 0 -> best=4
price=3 -> 3-1=2, not > 4 -> best stays 4
price=6 -> 6-1=5 > 4 -> best=5
price=4 -> 4-1=3, not > 5 -> best stays 5
-> return 5   (buy at 1, sell at 6)
```

Notice there's no set or dict here at all — unlike Day 3, this problem only needs two running numbers. That's the actual skill Day 4 is building: recognizing when a hash-based structure is overkill and a couple of tracked variables is the right tool.

### Why the greedy works

At every day, `price - min_price` is the best possible profit *if you sell today*. Because `min_price` only ever gets smaller (never resets upward), by the time you reach the true best-selling day, `min_price` already holds the true best-buying day that came before it. One pass is enough because you never need to look backward — the running minimum already remembers everything relevant about the past.

## ⚡ FASTAPI — PUT & DELETE, Completing CRUD

### Intuition

Day 3 gave you POST (create). Two verbs are left to make this full CRUD: **PUT** to replace an existing resource by id, and **DELETE** to remove one. Both need a way to *find* a resource by id first — which is exactly the dict-by-id pattern from today's Python block.

### The Essentials

```python
from fastapi import FastAPI
from pydantic import BaseModel
from typing import List

app = FastAPI()

class StockIn(BaseModel):
    ticker: str
    prices: List[int]

stock_db = {}       # dict keyed by id — today's "database"
next_id = 1

@app.post("/stocks")
def create_stock(payload: StockIn):
    global next_id
    stock_id = next_id
    stock_db[stock_id] = payload.model_dump()
    next_id += 1
    return {"id": stock_id, **stock_db[stock_id]}

@app.put("/stocks/{stock_id}")
def update_stock(stock_id: int, payload: StockIn):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}
    stock_db[stock_id] = payload.model_dump()   # full replace
    return {"id": stock_id, **stock_db[stock_id]}

@app.delete("/stocks/{stock_id}")
def delete_stock(stock_id: int):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}
    removed = stock_db.pop(stock_id)
    return {"deleted_id": stock_id, "ticker": removed["ticker"]}
```

### PUT vs. POST — the distinction that trips people up

POST means "create a new resource, server assigns the id." PUT means "replace the resource at this specific id with exactly what I'm sending" — the client names the id in the URL, and the whole resource is overwritten, not merged. That's why `update_stock` does `stock_db[stock_id] = payload.model_dump()` instead of updating individual fields.

We're keeping error handling simple today (`{"error": "..."}` instead of a real 404 status) — proper `HTTPException` with correct status codes is Day 6's topic. For now, CRUD is the only new concept.

## 🔗 COMBINED TASK — Wiring All Three

The dict-by-id pattern from Python becomes your stock "database," and the Best Time to Buy/Sell greedy runs against data pulled out of it instead of a hardcoded test list.

```python
# main.py — Day 4 combined endpoint

@app.get("/stocks/{stock_id}/max-profit")
def stock_max_profit(stock_id: int):
    if stock_id not in stock_db:
        return {"error": f"stock {stock_id} not found"}

    prices = stock_db[stock_id]["prices"]
    min_price = prices[0] if prices else 0
    best_profit = 0
    for price in prices[1:]:
        if price < min_price:
            min_price = price
        else:
            best_profit = max(best_profit, price - min_price)

    return {"id": stock_id, "ticker": stock_db[stock_id]["ticker"], "max_profit": best_profit}
```

## 🔑 CONCEPT ANSWER

**Question:** "Why does `dict.get(key, default)` exist when `dict[key]` already works?"

**Answer:** `dict[key]` raises a `KeyError` the instant the key is missing, which is correct when a missing key really is a bug — but most real code needs to *ask* "is this here?" without crashing, especially inside a loop where you don't yet know if a key exists (like building a frequency count). `dict.get(key, default)` returns `default` instead of raising, which is what turns `counts[ch] = counts[ch] + 1` (crashes on the first new character) into the one-liner `counts[ch] = counts.get(ch, 0) + 1` (always safe). Reach for `[]` when a missing key is exceptional; reach for `.get()` when a missing key is an expected, normal case.
